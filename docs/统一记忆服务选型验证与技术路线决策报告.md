# 统一记忆服务选型验证与技术路线决策报告

> 报告状态：阶段归档  
> 日期：2026-09-21
> 适用范围：统一记忆服务 MVP 技术路线、数据模型验证及后续工程实施  
> 结论性质：研发路线决策，不等同于生产上线许可

---

## 1. 报告目的

本报告对 Mem0、EverOS 与 Honcho 的验证和源码核查结果进行统一归档，回答三个问题：

1. 是否存在一套可以直接作为统一记忆服务完整底座的开源框架；
2. 三套方案分别适合复用或借鉴哪些能力；
3. 第一阶段采用什么技术路线，当前工程验证取得了什么结论，以及下一步如何实施。

本报告在原《selection_decision_explained.md》基础上补充 Honcho 结论，并结合《统一记忆服务数据模型详细设计规范 V1.0（冻结版）》和《统一记忆服务数据模型验证实施方案》形成最终阶段决策。

---

## 2. 验证范围与证据边界

三套方案的证据类型并不完全相同，结论需分层理解：

| 方案 | 本阶段主要证据 | 可以支持的结论 | 不能直接支持的结论 |
| --- | --- | --- | --- |
| Mem0 | 40 项能力测试、两轮运行、Email Agent 接入、源码复核 | 当前受测路径下的写入、检索、范围过滤和接入表现 | 完整治理能力、生产可靠性和总体平台改造成本 |
| EverOS | 40 项能力测试、两轮运行、Email Agent 接入、源码及相关模块复核 | 当前 Episode 检索路径的表现，以及已有画像、事实和维护模块的可借鉴性 | 仅凭 8/40 判断整个平台能力弱或改造成本必然更高 |
| Honcho | 已有多 Agent MVP 实践、主干版本源码与数据模型核查、真实历史库盘点及代表性小批量迁移 | 关系模型、分层记忆形成、依赖失效与后台维护流程的设计价值，以及当前样本的迁移可行性 | 未完成同口径 40 项测试；代表性样本不能证明全量迁移、生产迁移服务和生产规模可靠性 |

因此，本报告不将三个框架的单项分数直接排列为“平台优劣”。Mem0 与 EverOS 的测试主要回答现有适配路径能否满足业务用例；Honcho 的核查主要回答哪些底层模型和治理机制值得进入自有设计。

---

## 3. Mem0 与 EverOS 验证结果

### 3.1 核心结果

在当前完整判定口径下，两轮测试结果一致：

| 指标 | Mem0 | EverOS |
| --- | ---: | ---: |
| 完整能力用例 | 32/40 | 8/40 |
| Email Agent 任务完成 | 3/3 | 2/3 |

该结果包含内容召回、范围隔离、来源、写入方式、中文处理等完整条件，并非单纯统计“是否找到相关文本”。EverOS 的多个正向案例因缺少逐消息来源、直接录入能力或索引覆盖问题未通过，其 8 个通过项主要为负例和隔离例；因此 8/40 不能解释为“仅有 8 次找对内容”。现有语义判分仍需人工抽验，可靠性、恢复和容量验证尚未完成。

### 3.2 Mem0 结论

Mem0 的优势是调用和接入链路简洁，语义搜索、范围过滤、直接录入和基础 CRUD 已有可用路径，当前 Email Agent 验证也全部完成。从快速接入单个业务、验证检索闭环的角度看，Mem0 仍是三个方案中较轻量的组件候选。

但本轮暴露了影响可信度的阻塞问题：

- 写入去重未正确纳入业务域、项目域等治理范围，相似内容可能跨范围互相影响并被静默跳过；
- 重要指令存在漏提取，中文输出依赖额外配置，重复运行结果存在波动；
- 当前来源实现主要证明 metadata 可透传，尚未证明每条事实与具体原消息精确对应；
- 来源依赖、事实与画像分层、冲突、TTL、级联失效、派生重建和审计仍需统一服务自建。

因此，Mem0 适合保留为**简洁 API、模型与向量适配、现有试点兼容层的参考或局部组件**，不再作为统一记忆服务的默认完整底座。原“优先推进 Mem0”的结论仅在“沿用原测试适配路径快速完成单业务试点”的范围内成立。

### 3.3 EverOS 结论

EverOS 的优势是对长对话、事件变化和分层记忆对象的组织更完整，已有 Episode、AtomicFact、显式/隐式 Profile、Reflection、AgentCase/AgentSkill 等模块；本轮受支持写入未观察到 Mem0 同类提取遗漏，对否认、转述等语气的保留也较忠实。

当前主要问题包括：

- 同一用户不同项目的检索索引可能相互覆盖，造成原始内容仍在但查询无法命中；
- 结果只能稳定追溯到整段会话，缺少事实到具体消息的精确证据；
- 缺少直接保存已确认规则或案例的公开入口；
- 部分中文内容被转写为英文，影响中文检索；
- Markdown、SQLite 与 LanceDB 之间的数据身份和一致性仍需专项验证。

因此，EverOS 不适合直接按当前存储体系整体接入，但其 **EverAlgo 抽取、画像与事件整理算子，以及事实—画像—经验的职责拆分**具有较高复用价值。建议优先按独立算子接入统一候选对象，不整体搬入多套持久化体系。

## 4. Honcho 补充核查结论

### 4.1 已验证价值

已有 MVP 实践已证明：Honcho 可以承载不同 Agent 的交互；多个 Agent 可围绕同一用户形成不同记忆视角；公共背景与 Agent 专属记忆可以分开使用，并可结合任务进行召回路由和上下文组装。该实践说明“分域记忆＋召回路由＋上下文组装”的基本链路可行，但尚未证明生产成熟度、多用户并发能力和规模化产品价值。

源码核查进一步确认，Honcho 最值得参考的不是单一 search 接口，而是以下底层组织方式：

1. **关系型数据组织。** Workspace、Peer、Session、Message、Collection、Document、DocumentSource、向量状态和 QueueItem 已形成“原始交互—记忆结论—依赖关系—派生维护”的基本结构。
2. **分层记忆形成。** Deriver 面向显式事实，Dreamer 面向演绎、归纳和画像维护，可将高频事实抽取与低频画像、推理整理分开执行。
3. **依赖失效传播。** `process_scope_removal()` 已实现上游移除、派生结论递归停用、向量与缓存清理、画像重建和高阶记忆重组，是来源删除联动的主要设计参考。
4. **持久任务与补偿。** 向量同步包含 pending、synced、failed、重试与补偿机制，可用于设计异步任务状态机和失败恢复。

### 4.2 不能直接照搬的部分

Honcho 原生语义与统一记忆服务仍存在明显差距：

- observer/observed 表达观察视角和被描述对象，不等于归属、访问权限或业务适用范围；
- DocumentSource 主要连接结论与结论，原始消息到事实的精确证据仍需补建；
- 显式结论可能共享整批目标消息 ID，尚未达到每条事实的逐消息溯源；
- peer card 是 JSON 中的文本列表，不是可独立编辑、追溯、失效的画像属性表；
- 业务域、项目域、TTL、冲突、审计、租户复合约束和授权控制需按公司语义新增；
- Honcho 采用 AGPL-3.0，设计借鉴与直接引入、修改代码需要分别评估，首期默认作为设计参考；
- 当前已完成本机 Honcho 真实表结构、数据量和来源完整度盘点，并完成代表性小批量迁移；全量迁移、生产迁移入口及迁移后的画像重建仍未实施。

### 4.3 Honcho 定位

Honcho 不作为“原样部署即可满足要求”的完整底座，而作为**自有权威数据模型、事实到推理的分层形成、来源依赖失效和后台维护流程的主要设计参考**。现有 Honcho 消息与 Document 作为需要承接的历史资产，通过单向迁移映射进入新模型，不默认全量重新抽取。

## 5. 综合选型决策

### 5.1 最终决策

本阶段不选择 Mem0、EverOS 或 Honcho 中任意一套作为无需改造的完整统一记忆底座，采用以下组合路线：

> **建设以 PostgreSQL 15+ 和 pgvector 为基础、由统一记忆服务掌握权威数据模型的自有核心；以 Honcho 的关系型组织、分层形成和依赖失效为主要设计参考，以 EverOS/EverAlgo 的抽取与画像算子作为重点复用候选，以 Mem0 的简洁接口和模型适配作为 API 与兼容层参考。**

| 层次 | 决策 | 主要原因 |
| --- | --- | --- |
| 权威数据与治理 | 自有统一数据模型 | 来源、归属、范围、证据、版本、状态和审计必须由统一服务掌握 |
| 底层模型与维护流程 | 主要参考 Honcho | 与“来源—事实—推断—画像—派生更新”结构最接近 |
| 记忆形成算法 | 优先评估 EverOS/EverAlgo 独立算子 | 已有事实、画像、事件和经验等职责拆分，适合包装成候选生成器 |
| 接口与存储适配 | 参考 Mem0 | 接口轻量，模型、Embedding、向量存储适配较清晰 |
| 历史数据 | 迁移现有 Honcho 数据 | 保留原消息、结论、来源粒度和类型，缺失证据如实标记 |

首期不将三套完整服务串联运行，不建设任意后端热切换平台，也不同时维护多条功能相同的抽取链。开源组件只在明确的抽取器、画像生成器、检索适配器等边界内复用，所有正式数据统一进入自有模型。

### 5.2 决策变化说明

原测试报告将问题定义为“Mem0 与 EverOS 哪一套更适合先做业务试点”，在该范围内，Mem0 的 32/40 和 Email Agent 3/3 支持其成为近期受控试点候选。

随着目标扩展为跨 Agent 的统一记忆服务，选型标准新增了精确来源、事实/推断/画像分层、多来源依赖、冲突和版本、TTL、删除联动、派生重建、审计及历史数据迁移。按照这些要求，框架测试分数不足以决定平台底座，决策因此由“选择一套完整框架”调整为“自有权威模型＋分层借鉴和局部复用”。这不是否定原测试结果，而是扩大目标后对技术路线作出的收敛。

## 6. 已冻结的数据模型概要

数据模型 V1.0 已冻结为七张运行期核心表和一张迁移辅助表：

| 类别 | 核心对象 | 主要职责 |
| --- | --- | --- |
| 原始来源 | `source_record` | 保存对话、文档、工具结果、人工录入等原始记录及版本，是追溯和删除联动的起点 |
| 正式记忆 | `memory_item` | 保存事实、推断、技能经验和公共规范，记录主体、业务域、项目域、状态、版本和有效时间 |
| 用户画像 | `profile_property` | 保存由事实或推断投影出的当前属性，不将画像作为无来源事实库 |
| 证据关系 | `memory_evidence` | 表达来源到记忆、记忆到推断、记忆到画像的依赖；证据组采用组内 AND、组间 OR |
| 向量投影 | `memory_embedding` | 保存与记忆内容版本、模型版本绑定的向量；失效记忆在线立即排除 |
| 异步任务 | `memory_task` | 承担事务出箱和后台作业队列，支持幂等、优先级、租约、重试和版本防覆盖 |
| 变更审计 | `memory_audit_log` | 只追加记录关键变更的操作者、原因、前后状态和关联链路 |
| 迁移映射 | `external_entity_mapping` | 维护 Honcho 等外部实体到新模型的稳定映射，保证迁移幂等与可追溯 |

模型统一采用 `tenant_id` 进行租户隔离，区分输入者、归属主体、内容关联对象和适用范围；业务域、项目域与授权控制解耦。来源更新、纠正、TTL 到期或删除后，在线检索先立即停止使用无效内容，再通过持久任务完成依赖检查、画像重建和向量清理。首期授权关系仍由独立控制面负责，不在记忆表中混入 Agent ACL。

## 7. 数据模型工程验证工作与结论

### 7.1 验证目的

本阶段没有直接开发完整产品，而是先把冻结的数据模型落到真实数据库中，通过可重复实验回答以下
关键问题：模型能否阻止跨租户和非法数据关系；一条记忆能否追溯到原始来源；来源删除、过期或
纠正后，旧记忆能否及时停止使用；后台任务失败、重试或并发执行时是否会造成重复或旧数据覆盖；
不同用户、Agent、业务和项目之间能否正确隔离；现有 Honcho 历史数据能否解释并迁入新模型。

这样做的目的是在投入核心服务和业务接入开发前，先排除底层模型需要推倒重来的风险，并验证
后续写入、检索、治理和历史数据承接都有可实施的基础。

### 7.2 已执行的工作与实验

| 验证方向 | 执行内容 | 实验结果及意义 |
| --- | --- | --- |
| 数据库结构与隔离 | 在独立 PostgreSQL 环境中落地七张运行表和一张迁移映射表，反复执行建库、回滚和重建；主动写入跨租户、非法关联、重复记录和越界数据 | 数据库能够拒绝非法写入，升级和回滚可重复执行，说明核心隔离和一致性不依赖人工约定 |
| 来源追溯与生命周期 | 构造单来源、多来源共同支撑、多个独立来源、来源删除、内容纠正、争议状态和到期失效等场景 | 仍有独立有效来源时记忆继续可用；全部依据失效后立即停止检索，并能继续触发推断、画像和向量的后续处理 |
| 后台任务可靠性 | 使用多个并发处理实例模拟任务领取、优先级、超时接管、失败重试和旧任务延迟返回 | 同一任务不会被重复处理，处理实例异常后可安全接管，旧版本结果不能覆盖新状态，说明后台治理链路具备一致性基础 |
| 范围检索与性能冒烟 | 构造两个租户及用户、Agent、公司三类记忆，覆盖多个业务域和项目域；装载 3000 条虚构记忆，检查范围过滤、失效数据排除、向量检索和数据库执行计划 | 跨租户和越权范围数据未泄漏，失效或过期内容不会进入结果；主要查询在当前验证规模下耗时约 1～30 毫秒，未发现明显结构性退化。该结果用于工程可行性判断，不代表生产容量承诺 |
| Honcho 历史数据盘点 | 对真实 Honcho 数据库进行只读统计，核对 26 个会话、142 条消息、268 条记忆文档及其来源关系，识别缺失引用和无来源数据 | 确认了消息与记忆文档的实际关联方式，并形成对缺失来源如实标记、不伪造关系的处理规则 |
| 代表性迁移实验 | 从真实数据中选择 10 个会话、116 条消息和 50 条记忆文档执行试迁移，并进行重复执行、数量对账、来源完整性及源库前后指纹检查 | 试迁移形成 50 条新模型记忆及 84 条来源与推导关系；第二次执行未产生重复数据，未出现悬空关系，源库内容未发生变化，证明当前样本的迁移方案可行 |

### 7.3 阶段结论与边界

综合验证未发现需要调整整体技术路线或重构核心字段的问题。租户隔离、来源追溯、多来源有效性、
失效传播、任务一致性和范围检索均达到进入核心服务开发的条件，数据模型 V1.0 结论为：

> **GO：可以作为统一记忆服务核心功能开发的工程基线。**

该结论只说明底层模型和关键治理机制可行，不等同于完整服务已经开发完成，也不代表已经达到
生产容量或上线标准。Honcho 仅完成代表性小批量试迁移，尚未进行全量迁移；当前迁移程序也是
本地验证工具，正式迁移管理入口、自动化作业和迁移后的完整画像处理仍待后续建设。

## 8. 下一步执行计划

下一阶段从“验证模型”转入“建设服务”，按以下顺序推进：

1. **建设核心接入与读写能力。** 提供统一的来源写入、已确认记忆录入和查询入口，落实租户隔离、权限边界、变更审计和重复请求保护，形成可供业务系统稳定调用的基础服务。
2. **建设记忆形成与检索能力。** 接通事实抽取、重复判断、来源关联和向量生成，形成面向用户、Agent 和公司公共知识的分路检索能力。
3. **补齐生命周期与画像治理。** 实现到期处理、来源删除联动、推断重算、向量清理和用户画像重建，确保数据从产生到失效均可追溯、可修正。
4. **完成 Email Agent 最短业务闭环。** 用真实邮件场景验证写入、召回、反馈和纠错链路，观察数据质量、响应延迟、隔离效果和审计完整性，并据此收敛服务接口。
5. **扩展 OpenClaw 插件和命令行接入。** 在核心接口稳定后提供标准化接入方式，使不同 Agent 复用同一套记忆治理能力。
6. **最后实施正式迁移。** 核心服务及后台处理稳定后，再建设受控迁移管理入口和内部自动化作业，完成身份映射确认、迁移预演、审批、分批执行、断点恢复、结果对账和状态查询；使用专用只读账号完成 Honcho 全量迁移。

迁移安排在最后，是为了保证历史数据进入新系统后，能够立即使用完整的检索、失效处理、向量更新
和画像重建能力，避免先迁数据、后补治理造成重复处理或数据状态不一致。

## 9. 阶段进展总结（领导汇报版）

1. **技术路线已经确定。** Mem0、EverOS 和 Honcho 均有可借鉴能力，但没有一套能够直接满足统一记忆服务的完整要求；项目采用“自有权威数据模型＋分层复用开源能力”的路线，避免被单一框架的数据结构和授权边界锁定。
2. **数据模型验证已经完成。** 已在真实数据库中完成结构落地，并围绕租户隔离、来源追溯、多来源有效性、数据到期与删除联动、后台任务一致性、范围检索和性能进行了系统实验。结果表明核心模型能够支撑下一阶段服务开发，未发现需要推倒重来的结构性问题。
3. **历史数据迁移路径已经验证，但尚未全量迁移。** 已完成 Honcho 真实数据盘点和代表性小批量试迁移，重复执行未产生重复数据，来源关系可对账，源库未被修改。该实验确认了迁移方案方向，正式迁移服务和全量迁移安排在核心能力稳定之后实施。
4. **下一阶段转入核心服务建设。** 先完成统一读写、记忆形成、检索、生命周期和画像治理，再用 Email Agent 验证最短业务闭环，随后扩展 OpenClaw 接入；Honcho 全量迁移作为最后阶段执行，以降低历史数据承接风险。
