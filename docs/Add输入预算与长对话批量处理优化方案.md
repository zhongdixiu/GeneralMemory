# Add 输入预算与长对话批量处理优化方案

更新日期：2026-10-14。状态：历史截断和治理载荷精简已实施；验证记录见第 8 节。

本文替换此前分三阶段、要求关联历史完整保留的设计，按后续讨论收敛为当前可执行方案。Add 的公共消息格式维持现状，tool 字段和 assistant.tool_calls 仍在 metadata 内。

## 1. 前面讨论的结论

故障任务 `tsk_8c8288f581d84aeca1f898d8710cb226` 的目标正文只有 22 个汉字，失败发生在提取后的治理阶段。

当时按数据库候选重建的请求为 9997 **字节估算单位**，允许输入为 `12000 - 2048 = 9952`。9997 不是 tokenizer 的 token 数，也不是当时冻结的原始请求；它说明默认 10 条候选就足以触发旧检查。

| 原排查项 | 字节数 |
| --- | ---: |
| 治理提示词 | 2727 |
| 候选记忆正文 | 467 |
| 候选其他字段、字段名和 JSON 结构 | 5477 |
| 当前事实 | 356 |
| 目标消息 | 419 |
| 外层结构与固定预留 | 551 |

最先要解决的是重复结构，不能把“输入超限”简单归因于用户说得太长。长 Agent 回复还有第二个问题：旧路径会为纯辅助消息切很多片并调用模型，提前耗尽每任务 20 次调用额度。

本轮参考本地 Mem0 的两点：记忆 ID 使用请求内短编号，历史正文逐条截到 300 字符。Mem0 源码见 `/home/zhongdixiu/codes/mem0/mem0/configs/prompts.py` 中 `_format_conversation_history()` 和 `_truncate_content()`。本项目的历史截断只在所选原文整体放不下时启用，保留现有最近 30 条普通历史窗口和结构关联检索。

## 2. 治理候选：压缩表示，保留比较信息

实现文件：`src/memory_cmic/model_input.py`、`providers.py`、`worker.py`。

1. 模型请求统一使用紧凑 JSON，去掉结构中的多余空格，不改正文内空格。
2. 候选使用 `m0`、`m1` 等短编号。模型输出中的 memory_ids、historical_before_id 在 Provider 内还原后再进入原有校验、证据和提交逻辑。未知编号被拒绝；不替换正文内的同名字符串。
3. 候选完全相同的字段提取到 `candidate_defaults`。各候选只传自身差异，提示词明确合并规则。
4. statement_order 内重复的 Agent、来源、会话等信息提取到 `statement_order_defaults`。候选未提供顺序或顺序为 null 时，不应用这组默认值。
5. 模型候选保留正文、业务与项目条件、明确截止时间、来源陈述时间、状态、争议组和顺序。数据库到期时间 `expired_at` 已在候选筛选中用于排除过期项，且可能只是系统 TTL，不再送模型；明确截止时间仍由 `explicit_expired_at` 表达。完整候选继续参与服务端校验和提交前检查。
6. `source_message_ids` 是记忆内部来源元数据，服务端仍用于未知时间下的纠正校验。模型不再收到原始 ID 列表；仅对旧声明时间未知的候选发送 `shared_source`，表示它与本次事实的引用消息是否重合。模型不能根据 ID 读取旧原文；证据记录继续从完整事实的 `message_ids` 建立。
7. 当前事实的 `project_limited` 可由 `project_context` 推导，`retention_kind` 是存储期限策略；两项不再送治理模型。服务端仍使用完整事实计算记忆生命周期。
8. 治理只发送本次事实 `message_ids` 引用的当前用户消息，保留 `message_id`、`role`、原文、可信来源时间、时间来源和原始陈述顺序。`received_at`、附件引用、回复链和其他抽取阶段的辅助字段不再重复发送。纠正引文仍由服务端对完整用户原文逐字校验；未引用的同片用户消息由各自事实独立治理。

示意：

```json
{
  "candidate_defaults": {"status":"active","project_context":null},
  "candidates": [
    {"id":"m0","memory":"用户喜欢简洁回复。"},
    {"id":"m1","memory":"用户要求周报用列表。"}
  ]
}
```

这不是数据库格式变更，不需要迁移来源或记忆 ID。不会截断候选记忆正文；末尾可能含项目、日期和适用条件。对多争议组、极长记忆仍可能超限，维持逐事实暂缓，不自动 ADD。`statement_order` 的会话标识现已做公共值去重；进一步改成同会话布尔值及顺序号会改变模型的时间判断输入，本轮暂不引入。

## 3. 历史：原文优先，超限后统一 300 字符

不增加语义分类器，不要求接入方判断哪些历史“真正必要”。已提供的 reply_to_message_id、turn_id、tool_call_id 继续用于查找和优先选择上下文；没有这些关联也使用最近历史。

历史处理规则：

1. 无正文、无工具调用、无附件引用的历史不进入模型请求；空文本的真实工具调用仍保留。
2. 当前用户消息先占用输入预算。若候选历史整体能放下，发送原文。
3. 若整体放不下，所有历史角色采用同一规则：正文最长保留前 300 个字符。普通历史与明确关联历史的截断长度相同。
4. 再按剩余空间选择：可用的关联历史优先，其次较新的普通历史，最终保持原始顺序。即使截到 300 字符仍放不下的消息也可能未被选入。
5. 无历史可发时省略 history 字段，继续抽取当前用户消息。它是否依赖缺失上下文，由抽取结果明确报告。
6. 可选 related_memories 状态提示仍要求完整原文支持；支持未提供完整时，去掉该状态提示，不让它阻塞当前消息。

截断是有损的，不能保证前 300 字符包含末尾限制。被截断的消息带 `truncated=true`，提示词要求不能将对未见完整方案的确认理解为无条件确认；缺少依据应输出 context_insufficient。真实模型检查曾在有截断标记时仍提取整套方案偏好。因此增加确定性校验：凡是引用被截断的其他历史消息的事实都不落库，返回 context_insufficient / HISTORY_TRUNCATED；同一消息的独立事实仍可保存。该规则不需要判断语义相关性，但会暂缓依赖历史前缀的事实；模型漏报历史引用的风险仍需质量评估。当前用户分片与自己的历史衔接共享消息 ID，引用当前分片不按另一条旧历史处理；恢复测试覆盖这一边界。

**数据库始终保存完整原文。** 截断只用于模型历史视图。start_char/end_char 对应实际提供区间，不把 300 字符扩写成完整来源证据；本轮引用截断历史的事实暂不建立正式证据。省略号不混入正文，以免破坏原文定位。

## 4. 当前消息与长 Agent 回复

- 当前 user 正文完整进入抽取；单条放不下时按字符位置分片，片段合起来覆盖全部原文。超长当前用户消息不按 300 字符静默截断。
- assistant/system/tool 都是辅助来源。纯辅助片不调用提取模型，记录 no_durable_value 并完成本次来源处理；这不表示来源无上下文价值，也不生成用户事实。
- 相邻辅助消息可放在一个内部处理片，完整保存；其长度不产生额外提取调用。
- 后续用户消息可以通过显式历史、已有会话上下文和关联 ID 使用这些辅助来源。当前批次里只把此前消息作为历史，不把后到消息倒置到前面的目标。
- 已完成分片的长用户消息作为后续历史时，恢复整个消息的原文视图再按历史规则裁剪，避免仅把最后一片误当整条消息。

来源、幂等和公共 role/metadata 契约沿用现有接口。

## 5. 预算计数与装配性能

本轮继续使用原有保守 UTF-8 字节估算，不声称已经获得模型精确 tokenizer，也不将字节直接除以一个常数冒充 token。

```text
单次估算输入 = system 的 UTF-8 字节数
             + 实际发送的紧凑 JSON 的 UTF-8 字节数
             + 512 固定预留
默认阈值 = 12000 - 2048 = 9952
```

规划器与 Provider 共用 extraction_payload/governance_payload，包括未知时间处理、timezone 和空 history 的省略。最终请求在发送前检查；过大时不发网络请求。Search、Profile 等既有 input_size 调用者保持原预算算法。

每次历史选择先算固定部分，每条历史每轮序列化一次，随后用字节长度加法装配。不会每加入一条历史就重算不断增长的整个请求。单条长目标仍可能进行有界二分定位；这属于分片工作，不调用远程计数接口。

## 6. 剩余超限与批量调用上限

**单次输入限制和任务总调用上限是两个不同限制。**

- 目标用户消息的元数据本身放不下时，该消息返回 context_insufficient / TARGET_METADATA_BUDGET_EXCEEDED，保留完整来源且不标记提取完整，其他消息继续。
- 压缩后治理仍放不下时，对该事实返回 context_insufficient / GOVERNANCE_BUDGET_EXCEEDED，不调用模型、不自动当成 ADD、不标记来源提取完整；同片其他事实继续处理。
- 每任务仍最多 20 次外部模型调用，包含抽取、embedding 批次、治理和场景归一化，失败调用也占额度。
- 达到任务上限后按既有规则结束：有已提交变更为 partial，否则 failed；不无限重试或重新排队。
- 50 轮用户消息即使每轮都很短，也可能仅抽取就需要 50 次调用。接口允许 100 条消息不等于默认成本预算保证任意 100 条全部处理完。
- 本轮消除了长辅助回复造成的额外调用，没有交付软调度额度或自动续跑机制。如业务需要大批量全量完成，应另行确定总成本额度和续跑契约。

治理预算未完成的来源可以按现有规则补充明确的用户陈述或调整服务预算后使用新幂等键重新评估；同一幂等键仍重放原任务。

## 7. 版本与上线

新 prompt_version 为 `p02-v14-lean-governance`。执行切片和预算继续随任务冻结；正在执行的旧 prompt 任务不能混用新规则。部署前先排空旧 Worker 任务，或对终态任务使用现有受控重处理命令。

不需要数据库 schema 迁移；不修改工具参数位置；不自动重跑原故障任务或重启服务。
