# Add 输入预算与长对话批量处理优化方案

日期：2026-10-13  
状态：设计方案，尚未实施。本文中的配置、错误码和内部结构，除明确标为“当前”的内容外，均为建议。  
范围：MemoryCMIC Add 的输入计数、请求格式、长对话分片、治理调用和批量执行。

## 1. 方案结论

本次优化首先解决“短文本被过早判为超限”和“长对话被拆成过多模型请求”，并为合法大批量提供有上限、可恢复的执行方式。

建议分三阶段实施：

1. **首期：修正计数，压缩格式，保持原文和判断规则。** 不通过删除 Agent 回复、截断历史或减少候选来换取请求变小。
2. **第二期：完善分片和批量续跑。** 达到一次 Worker 执行额度后保存已提交进度、重新排队；任务总成本仍有限制。
3. **实验阶段：评估基于证据引用缩小上下文。** 在完整上下文对照评估通过前，不进入默认生产路径。

参考 Mem0 的短编号、精简模型输入和批量处理方式。保留本项目的时间顺序、用户确认、纠正、争议组和证据完整性规则，不照搬 Mem0 的历史截断或 ADD-only 流程。

**不能承诺任意长度的对话都能完整处理。** 单次模型窗口、输出容量和任务总成本均有限；必须说明支持范围，并明确报告未完成的部分。

### 2.2 本次任务为什么失败

任务记录显示：原始目标消息为 22 个汉字，已提取出 1 条事实；状态 `failed`，错误为 `INPUT_PROCESSING_FAILED` / `governance input exceeds model budget`。`changed=false`、结果数为 0，没有提交新记忆；调用计数为 2。

当前预算配置：

```text
input_tokens = 12000
output_tokens = 2048
max_model_calls = 20

允许输入 = 12000 - 2048 = 9952
```

但 [input_size()](../src/memory_cmic/extraction_input.py) 实际计算的是：

```python
len(system.encode()) + len(json.dumps(payload, ensure_ascii=False).encode()) + 512
```

即 UTF-8 字节数加固定开销，不是模型 tokenizer 得到的 token 数。这是当前明确采用的保守估算，配置名称容易让人误解其单位。

按排查时数据库中的默认 10 条候选重建，输入组成如下：

| 内容 | 字节数 |
| --- | ---: |
| 治理系统提示词 | 2727 |
| 10 条候选的记忆正文 | 467 |
| 候选的其他字段、字段名及 JSON 结构 | 5477 |
| 当前提取事实的 JSON | 356 |
| 当前目标消息及元数据 | 419 |
| 外层 JSON 结构 | 39 |
| 固定开销预留 | 512 |
| 合计 | 9997 |

**9997 是当前候选重建结果，不是任务冻结的完整治理请求大小。** 当时的实际候选列表未保存；相似检索和争议组展开还可能增加候选。因此只能说明默认候选集合已经足以触发预算检查，不能断言原请求恰好只超出 45。

### 2.3 长对话存在另外两类限制

第一类是输入容量。当前提取提示词占 7870 字节，在 9952 的阈值下，仅剩约 2082 字节容纳正文和消息结构。长 Agent 回复会被拆成很多片，切片间还会重复携带历史和衔接内容。

第二类是任务调用总数。当前每次抽取、embedding 批次和治理等调用都计数；达到 20 次即终结。输入能分片不等于任务能完成。

本地合成数据实验使用当前 `build_slices()`：

| 输入 | 切片数 | 上下文预算错误片数 |
| --- | ---: | ---: |
| 10 轮；每轮短用户消息＋500 字 Agent 回复；无显式回复关联 | 21 | 0 |
| 10 轮；每轮短用户消息＋2000 字 Agent 回复；无显式回复关联 | 91 | 0 |
| 10 轮；每轮短用户消息＋2000 字 Agent 回复；后续用户显式回复上一条 Agent 消息 | 91 | 0 |

这些是切片规划结果，没有调用模型。“错误片数为 0”不证明分片后的语义完整。每个正常切片至少一次抽取，91 片不能在当前 20 次任务额度内处理完。

近似调用量可表示为：

```text
总调用 = 抽取调用 + embedding 批次调用 + 治理调用
       + 场景归一化等附加调用 + 重试/恢复调用
```

不能把 `max_model_calls` 理解为“允许处理 20 条消息”，也不能通过增加单次输入窗口保证它一定够用。

### 2.4 治理阶段的额外开销

当前 `_plan_decisions()` 针对每条事实分别治理，每次传入 `fact + candidates + 当前切片全部 targets`。同片 Agent 长回复可能随多个事实重复发送。

候选规则是同范围内的最近 10 条，加相似检索返回的最多 5 条中达到阈值者，再展开被选中的完整争议组。普通并集不超过 15 条，争议组展开可以超过此数。

提取和治理使用不同提示词、不同载荷。提取阶段装得下，不能证明治理阶段也装得下。

## 4. 必须保留的正确性边界

### 4.1 关联与语义必要性不同

| 可用信号 | 程序能确定的内容 | 不能据此推断的内容 |
| --- | --- | --- |
| `reply_to_message_id` | 明确回复哪一条消息 | 其他历史都无关 |
| `turn_id` | 消息属于同一回合 | 同回合每个字符都与每条事实有关，或跨回合一定无关 |
| `tool_call_id`、`tool_calls` | 工具调用与结果的结构关联 | 工具输出一定正确或已经得到用户确认 |
| 提取结果 `message_ids` | 模型声称引用了哪些消息 | 引用已经完整、足以支持事实 |
| 向量相似度 | 文本可能相关 | 低相似度的否定、限制、纠正可以安全删除 |
| 消息较旧、较长或来自 assistant | 消息的形式属性 | 消息没有证据价值 |

例如“继续按之前的方案”可能依赖早期方案和中间追加的“只用于测试环境”。没有结构化回复关系时，简单规则无法找全依赖；模型也可能漏掉限制。

当前 `validate_fact_evidence()` 检查引用存在、至少引用一个目标用户消息，不验证语义支持是否充分。`context_insufficient` 可以表达模型发现的缺失，但模型未报告缺失不代表上下文一定完整。

### 4.2 首期禁止改变的行为

- 不把 Agent 回复一律删除，也不把只有 Agent/工具的内容自动当成用户事实。
- 不以固定 300 字、固定首尾段或模型摘要替代必要原文。
- 不因为某条历史没有显式关联，就把它认定为语义无关。
- 不通过删除候选或拆散争议组，使本应判重、纠正或争议的事实直接走 ADD。
- 不仅凭 `fact.message_ids` 将治理请求裁成“已确认完整的最小证据”。
- 不改变原始来源、原文字符位置、首次 `received_at`、消息声明时间、TTL、幂等身份和授权范围。

“首期不做语义裁剪”指不增加新的语义删减规则。现有系统已有最近 30 条普通历史窗口和按预算选取历史，无法保证无限远历史都被覆盖；本方案不把现有策略描述为全量上下文。

## 5. 首期设计：计数与请求格式

### 5.1 明确单次输入和输出的单位

建议内部明确以下概念，避免继续用一个字段表达多个含义：

| 概念 | 单位 | 作用 |
| --- | --- | --- |
| 模型上下文容量 `C` | token | 由已核实的模型规格提供；存在独立输入上限时同时遵守 |
| 应用输入上限 `I` | token | 控制单次请求的成本与规模 |
| 输出上限 `O` | token | 发给模型的输出约束；提取和治理可以有不同值 |
| 估算安全余量 `R` | token | 计数误差和消息封装开销的余量，不能与已计入的封装重复扣减 |
| 原始请求大小 | byte | 独立用于接入和资源保护，不冒充 token |

对输入输出共享上下文容量的模型：

```text
估算的完整输入 T <= min(I, C - O - R)
```

若模型另有独立输入上限，应再取该上限约束。不能未经核实把当前 `12000` 当作模型实际上下文容量。推理 token 的计费和窗口语义也必须按所用模型核实；当前 Provider 设置了 `enable_thinking=False`，不能假定所有替代模型都遵循这一行为。

环境变量的兼容决定必须显式记录。建议旧 `MEMORY_MODEL_INPUT_TOKENS` 在旧执行版本下保持原解释；新版本通过明确的配置映射进入新的预算结构，不能在旧任务重试时悄悄改变单位。

### 5.2 tokenizer 可行性先验证

当前依赖未提供与 Qwen 配套的 tokenizer。首期先完成一个可验证的计数选型，而不是直接引入一个名字相似的开源模型 tokenizer 并声称准确。

优先顺序：

1. 有官方对应的本地 tokenizer 时，固定其版本，离线加载，对最终消息结构计数。
2. 没有完全对应 tokenizer 时，可采用本地估算器，但必须标明估算身份，并在中文、英文、JSON、UUID、工具参数等样本上与 Provider 返回的 `prompt_tokens` 对照，确定余量。
3. 对未校准的模型保留明确的保守模式；按字节检查时标明 byte 限制。保守模式能用于过渡，但不作为“计数问题已解决”的验收依据。

不采用固定“字节数除以 3/4”作为适用于所有内容的准确计数。也不为每次候选装配发起远程计数请求。

计数器信息随任务冻结：模型标识、tokenizer/估算器版本、预算版本和安全余量。模型或估算方式更换后重新校准，不在执行中的任务上切换。

样本校准不构成所有输入都不会低估的证明。即使本地检查通过，Provider 仍可能因实际窗口或服务端封装拒绝请求。应识别结构化的输入超限错误，进入有限的重新分片或明确失败路径；不能把它包装成普通网络错误后原样重试。单个必要组无法缩小时终止该处理，不通过删掉证据强行通过。

### 5.3 对实际发送内容计数

规划器与 Provider 必须共享同一套请求构造和序列化规则：

```text
原始任务输入
  → 按阶段进行既有时间语义转换
  → 构造模型可见载荷
  → 序列化 system/user 内容及请求参数
  → 计算完整请求用量
  → 用同一份内容发送
```

注意：当前提取 Provider 会隐藏未知来源时间的时间锚点，并附加 `timezone`。计数不能只针对变换前的 `targets/history`。输出 schema、tools 等仅在实际发送时计入，不凭空计算没有发送的 Pydantic schema。

`QwenFactModel._json_completion()` 已保存 `last_usage`，可用于校准。后续应把 usage 绑定到具体调用和阶段，调用前清空旧值，及时读取并保存，避免将上次响应用量归到本次失败调用。

### 5.4 共用 `input_size()` 的迁移范围

该函数目前还被场景归一化、Search 适用性判断、Profile 和后台整理调用。直接替换其实现，会同时改变这些功能的有效阈值，例如 Profile 中的 `7000`。

首期建议：

- 保留旧函数和旧单位，明确标识其兼容用途。
- 新的 Add 执行版本使用显式预算和计数入口，覆盖抽取、场景归一化与治理阶段。
- 新旧计数方式必须显式传递，不能靠隐式全局切换。
- Search、Profile、后台整理暂时保持原行为；后续逐一迁移并重定阈值。

这里允许短期并存两个计数入口，是为避免改变无关模块；不扩展成通用 Provider 配置框架。

### 5.5 请求格式压缩

对同一个冻结切片和事实请求，格式转换保留相同的原文集合、候选集合、顺序和决策信息，只减少表示开销。新计数方式可能改变新任务的分片和可容纳历史数量，因此不要求新旧任务的中间请求逐字相同；保持既有历史窗口、候选召回规则，并验证最终事实和证据语义。

| 优化 | 实施规则 | 验证 |
| --- | --- | --- |
| 紧凑 JSON | 固定 `ensure_ascii=False` 和紧凑分隔符；计数与发送一致 | 解析后对象相同；字符串内原文和空白不被修改 |
| 短 ID | 消息、记忆使用分类型短编号，如 `s0`、`m0`；本地保存映射 | 全部输出引用反向解析后进入既有校验；未知编号拒绝 |
| 空字段 | 仅省略协议明确定义默认值、且缺省与原值等价的字段 | 正反转换测试；不能混淆未知时间与默认当前时间 |
| 重复公共字段 | 完全相同的来源身份/顺序上下文可以提到公共对象 | 不同来源仍显式区分；恢复原对象后时间比较结果一致 |

短 ID 只用于本次模型请求，不写入数据库主键、来源 ID、任务结果或证据。不得在原文字符串中做全局替换；例如原文中恰好出现 `m0` 仍应原样保留。

与模型约定的默认值必须写进版本化的输入说明。格式变换可以是数据上的可逆变换，但模型行为仍可能受表示影响，必须做真实模型回归，不能只凭“可逆”宣称输出必然相同。

### 5.6 字段保留原则

首期不直接删掉候选对象的语义字段：

- 记忆正文、业务和项目条件、状态、争议组决定能否比较、能否替代。
- `source_occurred_at`、`timestamp_origin`、`statement_order` 用于判断声明顺序。
- `explicit_expired_at` 与系统 `expired_at` 含义不同，不能合并。
- 来源引用参与用户更正与未知日期旧事实之间的关联校验。
- `effective_at` 不能拿来替代声明时间；是否仅在本地保留，应另做字段级契约评估。

内部保持完整候选记录用于 `_check_governance()` 和提交前校验。首期治理仍使用原有整片 `targets`，**不同时上线“仅发送 fact.message_ids”**；这能避免将格式优化和证据裁剪两个变量混在一起。

## 6. 第二期设计：长对话与超限恢复

### 6.1 保持当前消息角色契约

用户消息触发新增或维护事实；Agent/工具消息为理解提供上下文，单独出现不构成用户事实。首期仍按现有流程处理辅助消息，不仅凭角色跳过模型，也不改写其已处理状态。

后续若优化“纯 Agent 批次不抽取”，必须单独验证这些消息能被未来用户确认引用、证据撤回能生效，以及 `processing_results` 与来源状态兼容，不能顺便加入本方案首期。

### 6.2 分片的具体原则

1. 先以完整消息为单位装配，并保留当前已识别的回复、回合、工具和相关记忆支持关系。
2. 达到输入阈值后停止合片，后续消息进入下一片；不要把已放不下的必要依据移成“普通历史”以绕过检查。
3. 单条正文过长时保留现有按段落/字符位置分段机制，显式标记片段及原文位置。
4. 工具调用与结果作为结构关联处理；不把半段 JSON 参数当作完整工具调用。
5. 某个必要关联组完整内容确实放不下时，明确记录 `context_insufficient`；其他已有独立切片可以继续。

分段只保证可以逐段覆盖原文，不保证任意跨段语义自动保持完整。当前 256 字衔接也不是语义完整性证明。评估必须包含“关键限制在长回复末尾”等场景。

当前按字符位置二分寻找可容纳片段，依赖字节长度随正文增加而增长。换成 tokenizer 后，前缀 token 数可能因分词边界变化而局部减少，不能沿用二分并声称找到了严格最大的片段。建议按完整段落或有原文位置映射的候选边界装配，以最终完整请求检查为准；允许保守地少装一段，不截断字符或丢失后续区间。

同一来源有多个片段时，引用不能只按 `message_id` 判断正文已完整提供。需结合来源版本及 `start_char/end_char` 判断提供了哪些区间，避免把最后一片当成整条 Agent 方案。

### 6.3 输出预算单独处理

输入变大后，单次能提取的事实数量也可能增加，原输出额度未必够用。因此不能只提高输入上限：

- 输出预留随请求阶段确定，并受模型实际限制约束。
- 提取的 `finish_reason=length` 继续按可恢复切片处理，有限次拆分后明确失败。
- 拆分必须保留原目标字符位置和上下文，不把模型已截断的半段 JSON 当有效事实。
- 治理的输出截断不应原封不动重试直到耗尽额度；先明确是响应容量问题，再做有界调整。它与输入超限是不同错误。

不预设“一个切片最多 N 个事实”而静默丢掉后续事实；若将来限定事实数，必须具备明确的后续处理协议。

### 6.4 治理输入仍超限时

压缩和计数修正后，仍可能存在“单条事实＋原文＋完整候选集合”放不下的情况。处理顺序如下：

1. 确认是完整实际请求超限，并记录各部分计数。
2. 如果提取切片包含多个独立目标，评估在未提交前拆成更小提取片并重新提取；拆分次数有限、输入冻结、必须保留依赖。该策略需要专项测试后才启用。
3. 若一个关联组或争议组本身过大，报告治理输入超限，保留来源和已提交进度。

不将候选拆成几组各自裁决并立即落库。例如第一组 ADD、第二组 DUPLICATE 时，先落库会造成重复；跨组 SUPERSEDE / DISPUTE 也需要统一裁决。首期与第二期均不引入未经设计的分组投票或合并规则。

输入超限不是网络错误，不能原样自动重试。首期保留现有失败/部分完成语义，仅增加明确诊断；逐事实失败隔离涉及同片依赖和原子提交，留待单独设计，不能简单捕获异常后 `continue`。

## 7. 第二期设计：批量续跑与有限成本

### 7.1 拆分三种执行限制

| 限制 | 用途 | 达到限制后的行为 |
| --- | --- | --- |
| 一次 Worker 执行的调度额度 | 防止大任务长期独占 Worker | 在已提交切片边界让出，重新排队 |
| 错误重试额度 | 限制超时、限流、服务错误和恢复次数 | 耗尽后按已有提交情况结束为 failed/partial |
| 整个任务的硬成本上限 | 限制总模型调用与资源消耗 | 明确终结并报告未完成进度，不能重新排队绕过 |

现有 `MEMORY_TASK_MODEL_CALL_LIMIT=20` 是第三种限制。**不能只把它改名为调度额度，同时取消硬上限。** 第二期需要新增明确的调度额度；旧变量的硬限制语义保留，支持范围扩大时显式调整其值。

### 7.2 最小可行续跑方式

复用原任务 ID、`execution.next_slice`、冻结输入和结果，在已提交切片之间续跑；不先引入父子任务体系或逐事实持久化状态机。

```text
pending → processing
  → 执行一个或多个完整切片
  → 同事务提交记忆、证据、结果和 next_slice
  → 还有切片且达到调度额度：pending，释放租约
  → 切片全部完成：succeeded
```

正常让出不调用 `fail_and_retry_task()`，不增加 `attempt_count`，不重置累计调用量，不填写错误、不设置完成时间。

新增队列让出操作必须校验 `tenant_id/task_id/worker_id/lease_token` 和未过期租约，并原子清理 `worker_id`、`lease_token`、`locked_until`，设置新的 `available_at`。下一次领取继续现有进度。

同会话后序任务仍受前序 pending/processing 阻挡，避免跨批纠正顺序改变。其他会话可以获得调度机会；不宣称同一用户不同会话因此自动全局串行，仍依赖既有提交锁和状态复核。

### 7.3 调度额度只在安全点生效

当前治理决策和 embedding 没有全部作为可恢复的中间状态保存。若在治理到一半时释放任务，恢复后可能重复付费、重新生成决策。因此初版仅在切片提交完成后检查软调度额度。

这意味着一次执行可以超过软额度以完成当前切片。硬任务成本上限仍在每次调用前检查；若碰到硬上限，当前未提交切片不落库，已提交片保留。

调度前先确认剩余额度是否连下一阶段的已知调用都不够；可提前失败并避免部分无效调用。但抽取前无法准确预测事实数、场景归一化和重试量，不对总调用数作虚假的精确预测。

### 7.4 总成本与支持范围

接口当前最多 100 条 `messages` 和 100 条 `history_messages`，正文没有统一的长度上限。仅限制条数不能保证成本有限。

第二期上线前必须以评估结果明确：

- 支持的单消息长度、单批原文总量、关系链大小及典型事实数量。
- 对应的任务硬调用上限和允许的恢复次数。
- 超过支持范围时的接入或任务终态行为；若新增接入大小限制，应作为明确的 API 兼容变更单独发布。

本方案不凭空选一个新的硬上限，也不承诺 100 条任意长消息都成功。未完成容量评估前保留当前硬上限，不能仅上线调度续跑就宣称“大批量问题已解决”。

累计用量不会因让出、重试、进程重启或换 Worker 归零。实际调用已经发出但未收到响应时，usage 可能未知；调用次数仍计入，不能按零成本处理。

## 8. 性能设计：避免反复全量计数

### 8.1 计数步骤

每加入一条候选就重新序列化并 tokenize 整个增长中的请求，会重复处理前面的内容。候选等长时，处理量接近 `1 + 2 + ... + N`，具有平方增长风险。

采用：

1. 固定提示词和当前证据计算一次。
2. 每条消息、候选或不可拆分关联组预计算一次。
3. 装配时累加估算成本。
4. 对最终完整请求复核一次。
5. 如分项累加与整体计数存在边界差异，按合法分片边界缩小请求后再检查；无法缩小的必要集合明确报错。

tokenizer 在字符串拼接边界处的结果不一定可加，因此预计算用于快速装配，不能替代最终复核。不能为了满足“只检查一次”而绕过预算。

缓存限定在当前任务或工作单元，键包含内容、版本和请求格式版本；候选因同片前一事实发生变化时更新对应计数。不先引入全局缓存或外部缓存服务。

### 8.2 本地微基准

使用合成候选、当前 UTF-8/JSON 算法，5 次取中位数：

| 候选数 | 每次重算增长中的完整请求 | 分项预计算＋最终检查 |
| ---: | ---: | ---: |
| 10 | 0.329 ms | 0.120 ms |
| 100 | 22.075 ms | 1.068 ms |
| 1000 | 2606.270 ms | 11.361 ms |

此结果不包含 tokenizer、数据库和网络调用，不是生产 SLA。1000 条是压力场景，不能描述成当前常规候选数量。

实际 tokenizer 选定后重测 CPU 时间、内存、切片规划耗时和 p95；同时测数据库读写和模型调用次数。对当前十几条候选，性能优化优先级低于正确计数及减少过度分片。

### 8.3 其他可能开销

任务目前在 `payload.execution` 保存冻结输入、切片和进度。长任务生成大量重复历史片段时，会增加 JSONB 大小和每次保存成本。

首期先记录冻结载荷大小与写入耗时。只有计数修正后仍存在明显重复数据开销，才考虑将切片改为引用冻结消息及字符区间；需要保持来源版本、恢复行为和证据定位。该存储重构不与首期计数修复捆绑。

## 9. 诊断与错误表达

预算检查失败时至少记录以下非正文信息：

```text
stage / slice_index / fact_index
budget_version / payload_version / counter_id / model_id
measurement_unit
estimated_input_tokens / input_limit / output_limit / safety_margin
prompt_units / evidence_units / candidate_units
candidate_count / conflict_group_count
model_calls_total / next_slice / slice_count
```

分项 token 可能与整体 token 有边界差异，诊断中标明分项为估算；byte 模式不得把数值写进声称精确的 token 字段。错误日志不默认打印完整聊天和凭证。

建议内部区分：输入超限、输出截断、任务总成本耗尽、必要上下文不足。公共 `error.code` 首期保持兼容，在 `message` 或内部 diagnostics 中提供阶段与数值；新增公共错误码应在第二期同步文档和客户端契约测试。

`succeeded`、`results=[]` 仍不能单独代表“全部内容已记住”。对于上下文不足和未完成来源，继续依据 `processing_results` 与来源完成标记解释结果，不通过优化把它们改成 `no_durable_value`。

## 11. 验证与验收

### 11.1 确定性回归

| 场景 | 验收要求 |
| --- | --- |
| 原故障任务的脱敏固定样例 | 10 条短记忆的完整请求不因旧字节阈值误拒绝；真实支持窗口内完成正常治理 |
| 紧凑格式与短 ID | 可恢复原对象；原文未变；错误 ID、跨类型 ID 被拒绝 |
| 空字段和时间 | 未知时间不变成当前时间；显式过期与系统 TTL 仍能区分 |
| 预算边界 | 阈值内发送、阈值外明确处理；计数内容与实际发送内容一致 |
| 中英文、代码、emoji、JSON | 字符位置正确、计数方法明确；不因编码边界损坏原文 |
| 输出截断 | 有限次恢复，无半段 JSON 落库，无重复证据或遗漏完成标记 |
| 长 Agent 回复与用户确认 | 正确引用方案和确认；仅 Agent 陈述不生成用户事实 |
| 跨 30 条普通历史的显式回复 | 仍可找到已授权同会话来源，保持证据失效传播 |
| 同时间/迟到纠正 | 保持原声明顺序和迟到保护 |
| 多条争议组 | 不拆散组、不漏掉成员、不错误降级为 ADD |
| 超限必要关系组 | 明确未完成；不伪造成功或标记已完整提取 |
| 同批独立切片 | 已定义的独立切片可继续；未设计逐事实隔离前不改变同片原子性 |
| 续跑与重启 | 已提交切片不重复执行，冻结版本不变，累计用量不归零 |
| 租约竞争 | 旧 Worker 不能提交或让出新 Worker 已接管的任务 |
| 同会话后续批次 | 前序让出后仍保持顺序等待 |
| 硬总成本耗尽 | 有变更为 partial、无变更为 failed；无无限重新排队 |
| 共享计数函数调用者 | Search、Profile、后台整理在未迁移前行为保持原基线 |

复用现有 `test_extraction_input.py`、`test_add_context.py`、`test_fact_governance.py`、`test_task_queue.py` 和 Provider 测试，不为每个格式细节创建只复述实现的测试。增加测试主要用于证据、预算、迁移和恢复等真实风险。

### 11.2 真实模型对照

确定性测试不能证明模型理解等价。真实模型评估采用固定模型版本、配置、输入样本和人工确认的预期结果，逐条保存调用用量和差异。

至少包括：

- “就按第二个方案”，没有 `reply_to_message_id`。
- 方案在早期，中间补充“仅限测试环境”，最后再次确认。
- 用户在同片稍后否定或纠正先前内容。
- Agent 长回复末尾出现关键限制，用户确认整条回复。
- 工具调用、长工具结果、用户随后确认。
- 相同事实重复、跨项目同文本、未来规则、迟到状态更新、争议澄清。

对照应分别比较“相同完整输入的旧格式与新格式”，以及 P3 的“完整上下文与子集上下文”。不能把旧路径因预算失败产生的空结果当成语义质量基准。

关键错误如丢失限制、把 Agent 建议当用户确认、误覆盖较新事实，属于阻断上线问题。未观察到错误也只说明已测样本通过，不宣称可以可靠识别所有语义必要历史。

### 11.3 性能与容量评估

输入矩阵包含 1/10/50 轮对话，Agent 回复 500/2000/10000 字；50 轮对应当前 100 条 messages 上限。另测明确依赖链、单个超长消息、普通候选 10/15 条和大争议组。

记录：

- token 估算与 Provider 实际 usage 的误差。
- 切片数、抽取/治理/embedding/附加调用数、输出截断次数。
- 计数 CPU、规划耗时、数据库载荷大小与写入耗时。
- 端到端耗时、成功/部分完成/上下文不足比例。
- 事实遗漏、限制遗漏、错误替代和证据完整性。

上线前根据结果填写受支持容量和配置值，不预先承诺节省百分比或固定延迟。最终报告应区分格式节省、计数口径变化和实际 Provider token 节省，三者不是同一指标。

## 12. 升级、回退和故障任务恢复

1. 新任务冻结 `execution_version`、预算版本、计数器版本、模型标识和请求格式版本；字段名以实施时最终定义为准。
2. 存量执行状态缺少新版本字段时按旧版本处理，禁止直接用新 token 算法解释旧 `execution.budget`。
3. 优先排空旧任务后部署；需要并存时显式按版本路由。无法识别新格式的旧 Worker 不得领取新任务。
4. 保留来源、幂等键、证据与历史任务。回退时停止领取新版本任务，不把其冻结状态强行降级。
5. 原失败任务不会因修改环境变量自动恢复。同一幂等键仍返回原任务。
6. 修复验证后使用现有受控重处理命令创建新任务，并保留原任务审计：

```bash
poetry run python -m memory_cmic.add_management \
  --task-id tsk_8c8288f581d84aeca1f898d8710cb226 \
  --reason '输入预算与请求格式优化后复核'
```

上述命令是实施后的操作说明，本次编写文档没有执行重处理、修改任务、重启服务或调用真实模型。

## 13. 实施前仍需核实的事项

| 事项 | 为何必须核实 | 阻塞范围 |
| --- | --- | --- |
| 实际部署模型及计数器对应关系 | 闭源/别名模型不一定有精确本地 tokenizer | P1 新 token 计数上线 |
| 模型上下文、独立输入、输出限制 | 不能从应用默认 12000/2048 推断供应商能力 | 新预算配置 |
| 中文及结构化载荷估算误差 | 决定安全余量，避免把过严检查改成低估 | 计数验收 |
| 受支持的批量输入规模和硬成本 | 有限预算下无法承诺任意长批量完整成功 | P2 发布 |
| 新请求表示对治理质量的影响 | 数据可逆不等于模型输出行为相同 | 短 ID/默认值上线 |
| 证据引用完整性 | 当前 ID 校验不足以证明语义无损 | P3 上下文裁剪 |

这些事项不妨碍先准备格式转换、诊断与确定性测试，但不能以“已有设计文档”替代测量或验收。

## 附录 B：候选计数微基准复现

该实验比较当前 byte 算法的两种装配方式，不模拟真实 tokenizer 或模型延迟。分项字节累加在这里能精确匹配 JSON；token 累加不能据此作同样保证。

```bash
.venv/bin/python - <<'PY'
import json
from statistics import median
from time import perf_counter
from memory_cmic.extraction_input import input_size
from memory_cmic.providers import GOVERNANCE_PROMPT

base = {
    "id": "mem_" + "a" * 32,
    "memory": "用户希望每周一发送项目进度报告。",
    "business_domains": ["communication"], "project_context": None,
    "status": "active", "effective_at": "2026-10-13T07:43:12+00:00",
    "expired_at": None, "explicit_expired_at": None, "conflict_group_id": None,
    "temporal_kind": "current", "source_occurred_at": "2026-10-13T07:43:12+00:00",
    "timestamp_origin": "source",
    "statement_order": {"caller_agent_id": "example_agent", "source_system": "test",
                        "session_id": "example_session", "batch_seq": 12, "position": 0},
    "source_message_ids": ["msg_008"],
}
for n in (10, 100, 1000):
    candidates = [{**base, "id": f"mem_{i:032d}"} for i in range(n)]
    slow, fast = [], []
    for _ in range(5):
        start = perf_counter()
        for end in range(1, n + 1):
            input_size(GOVERNANCE_PROMPT, {
                "fact": base, "targets": [], "candidates": candidates[:end]
            })
        slow.append((perf_counter() - start) * 1000)
    for _ in range(5):
        start = perf_counter()
        costs = [len(json.dumps(c, ensure_ascii=False).encode()) for c in candidates]
        used = input_size(GOVERNANCE_PROMPT, {
            "fact": base, "targets": [], "candidates": []
        })
        for index, size in enumerate(costs):
            used += size + (2 if index else 0)
        actual = input_size(GOVERNANCE_PROMPT, {
            "fact": base, "targets": [], "candidates": candidates
        })
        assert used == actual
        fast.append((perf_counter() - start) * 1000)
    print(n, round(median(slow), 3), round(median(fast), 3), flush=True)
PY
```
