# 租户画像维度配置运行说明

对应迁移 `0012_profile_dimensions`。接入方按租户管理画像维度，维度由名称和描述定义，
系统根据有效记忆生成独立陈述。同一维度可以包含多条陈述，每条继续维护独立证据。

## 数据与默认配置

新增一张 `tenant_profile_config` 表：`tenant_id` 为主键，包含 `version`、JSONB
`dimensions` 和 `updated_at`。维度数组顺序即展示顺序，不单独创建维度表。

| 默认 key | 名称 |
|---|---|
| identity | 基本身份 |
| residence | 居住与生活背景 |
| education | 教育与学习背景 |
| occupation | 职业与当前角色 |
| relationships | 家庭与重要社会关系 |
| social_habits | 社交习惯 |
| diet | 饮食偏好与习惯 |
| dietary_restrictions | 饮食限制 |
| preferences | 兴趣与其他个人偏好 |
| communication | 沟通与协作偏好 |
| other | 其他长期背景 |

每个维度保存 `key`、`name`、`description`、`enabled`。默认描述包含收录范围和排除条件，
具体内容见 `src/memory_cmic/profile_config.py`。默认模板只用于首次初始化，不覆盖租户修改。

画像复用 `property_key` 保存稳定的维度 key；不再表示固定单值属性。取消原 active key
唯一索引，新增约束要求 active 画像有非空 key 和非空字符串值。旧画像的空 key、JSON 等
历史值保留在非 active 记录中。仓储写入改用 `create_profile()`，不会按相同 key 覆盖旧条目。

不匹配任何启用维度的内容不进入画像，底层事实保留。停用 `other` 可以关闭默认兜底。
描述用于分类，不能覆盖证据规则、放宽租户边界或授权模型猜测。

## 配置 API

`GET /api/v1/profile-config`：已认证的租户凭证可读取本租户配置，首次读取时初始化默认值。

`PUT /api/v1/profile-config`：需要现有 `can_manage_governance=true` 权限。请求为整体替换，
省略的原维度会被移除；若只修改一个维度，应先读取并提交完整列表。租户来自凭证，
请求不接受 `tenant_id`。

下面的请求有意将配置替换为两个维度：

```json
{
  "expected_version": 1,
  "dimensions": [
    {
      "key": "education",
      "name": "教育与学习背景",
      "description": "用户的学历、专业、学校和当前在读阶段，保留已毕业与在读的区别。",
      "enabled": true
    },
    {
      "name": "宠物背景",
      "description": "用户明确饲养的宠物及其长期习惯和限制，排除一次性活动。",
      "enabled": true
    }
  ]
}
```

新增维度省略 key，由后端生成 `dim_...`；更新原维度必须携带已有 key，不能自行指定新 key。
名称修改不改变 key。可以提交空数组，关闭全部画像维度。

响应为保存后的 `version` 和完整 `dimensions`。版本不匹配返回 `409 PROFILE_CONFIG_CONFLICT`，
重新读取后再编辑。未知 key、重复 key 或名称、空白内容、超出模型输入预算的配置均被拒绝。
最多 32 个维度，名称最多 128 字符，描述最多 2048 字符；启用维度总大小还受模型预算限制。

相同配置保存不增加版本、不创建任务。列表内容或顺序发生变化时版本递增，创建持久化
`profile_config_apply` 任务，并记录 `PROFILE_CONFIG_CHANGED` 审计。第一版整体重建，
因此纯排序变化也会重建。

## 生成、重建与读取

profile Worker 同时消费 `profile_config_apply` 和原 `profile_rebuild`。前者每批最多扫描
100 个用户，持久化分页游标，逐个复用原画像任务的合并、用户锁、租约和失败重试机制。
覆盖有记忆、已有画像或已有治理状态的用户；过时配置的调度任务直接结束。配置保存与
调度任务创建处于同一事务，不依赖 API 进程内后台线程。

模型输入包含启用维度，输出增加 `property_key`。服务端验证 key 属于当前配置，
验证 memory_id、精确 quote、非空陈述与证据。相同条件下的一条陈述不能归到两个维度。
一维多条、独立 OR 依据、来源失效传播和明确/推断标识继续保留。

候选指纹包含配置版本；模型调用期间配置变化，提交时通过配置行锁和版本复核拒绝旧结果，
随后重新排队。单用户重建原子更新画像及 `profile_config_version`，空结果也记录已应用版本。
关闭全部维度时不调用模型，旧画像及依据边按原机制失效。

`GET /api/v1/profiles?user_id=...` 保留 `profiles` 列表，增加：

```json
{
  "profiles": [
    {
      "id": "profile_example",
      "assertion_kind": "explicit",
      "property_key": "relationships",
      "property_value": "用户的妹妹喜欢画画",
      "value_type": "string",
      "business_domains": null
    }
  ],
  "config_version": 2,
  "applied_config_version": 2,
  "status": "ready"
}
```

`status` 为 `ready`、`pending` 或 `failed`；配置尚未应用时不输出旧配置画像。
读取配置列表即可展示无内容的维度，不需要生成“未知”陈述。多个条目可以有相同 key，
调用方应按 key 分组为数组，不得转换成 key 到单条记录的字典。
读取仍验证有效时间、证据、业务范围和推断准入；非空 key 不再绕过依据范围匹配。

## 背景信息边界

- 用户本人偏好与关系人信息分别归类，后者必须保留明确关系主语。第一版不跨事实合成人物身份。
- 已取得学历、出生日期等可以具有持续背景价值；历史依据可以参与蒸馏，但不能将过去就读、
  工作或居住改写成当前状态。临时事实、项目限定事实和无效依据仍被排除。
- 年龄保留可靠的时间条件；不根据无日期的年龄猜测生日或当前年龄。本次没有实现年龄自动计算。
- 推断仍默认关闭；历史背景候选扩展不放宽推断及其依据的 current/long_term 条件。
- 新抽取规则补充教育、关系人和年龄示例。存量事实的 retention_kind、TTL 和原始内容不被
  迁移改写；此前误分类为 regular 的当前背景，需要从原始来源重新评估才能补齐。
- 精确引用和维度校验不能保证语义正确，真实业务样本仍需检查人物归属、时间条件和分类边界。

## 上线与回滚

先停止旧版本 Worker，再升级代码和数据库：

迁移只创建重建任务，不会启动 Worker。当前 `docker-compose.yml` 仅启动 PostgreSQL；
API 进程及默认的 add Worker 不消费画像任务，需要单独保持 profile Worker 运行。

```sh
.venv/bin/alembic upgrade head
.venv/bin/python -m memory_cmic.worker --role profile
```

迁移为数据库中已有租户初始化默认配置，审计并失效全部旧 active 画像及其有效依据边，
保留历史记录，并创建租户批量调度任务。旧 key 不直接映射到新维度，由有效事实重新生成。
新租户在首次读取配置或处理画像时初始化。重建期间画像可能暂为空，事实检索继续可用。

出现维度配置变更审计或批量调度任务历史后，downgrade 会拒绝执行，要求显式制定数据转换方案。
恢复旧单值唯一索引时，同维度多条 active 记录也会阻止回滚。迁移不会删除历史或自动合并条目。
