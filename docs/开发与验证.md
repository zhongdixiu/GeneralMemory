# 开发与验证

以下命令在项目根目录执行，配置值使用自己的开发环境；不要提交包含真实 token、密码或模型 Key 的 `.env`。

## 1. 准备环境

项目要求 Python 3.11+、Poetry、Docker Compose。依赖和脚本入口见 `pyproject.toml`；数据库镜像见 `docker-compose.yml`。先从 `.env.example` 创建本地 `.env`，至少配置 PostgreSQL 密码、`MEMORY_DATABASE_URL`、`MEMORY_AUTH_CREDENTIALS_JSON`，按将运行的 Worker 配置模型 Key。

```bash
cp .env.example .env
# 编辑 .env 中的本地密码、服务凭证及模型 Key
docker compose up -d postgres
set -a
source .env
set +a
poetry install
poetry run alembic upgrade head
```

`docker-compose.yml` 只负责数据库。`MEMORY_DATABASE_URL` 的用户名、密码和端口应与 Compose 配置一致。不要在含业务数据的数据库上运行迁移回退或需要旧 schema 前置条件的迁移测试；先用独立测试库验证。

## 2. 启动所需进程

每个命令在已加载 `.env` 的独立终端运行：

```bash
poetry run memory-cmic-api
poetry run memory-cmic-worker --role add
poetry run memory-cmic-worker --role maintenance
poetry run memory-cmic-worker --role consolidation
poetry run memory-cmic-worker --role profile
```

API 默认监听 `0.0.0.0:8000`。按要验证的能力启动相应 Worker：Add 处理新来源；maintenance 处理向量、到期和依赖；consolidation 处理治理；profile 处理画像。缺少相应 Worker 时，API 仍可能成功入队，但任务不会自动完成。具体手动联调见 [ADD 接口运行说明](ADD接口运行说明.md) 和 [记忆治理后台运行说明](记忆治理后台运行说明.md)。

## 3. 先做一次端到端检查

1. 按 [ADD 示例](ADD接口运行说明.md#提交消息)提交一条使用当前凭证允许的 `source_system` 的用户消息，记录 `task_id`。
2. 按 [任务查询示例](ADD接口运行说明.md#查询任务)轮询，确认 Add Worker 消费。检查 `status` 和 `processing_results`，不要只看结果列表是否为空；重复事实可能只增加证据。
3. 用 [Search](Search与Profile接口运行说明.md#search)检索该用户。新事实的向量由 Add Worker 写入；maintenance 处理后续更新和删除所需的向量任务。没有结果时检查任务状态、事实有效性和模型配置。
4. 若涉及治理或画像，再启动对应 Worker，查治理运行、画像状态及审计 `correlation_id`。

自动化测试使用模型替身；它验证代码逻辑，不等同于真实模型的质量、延迟和成本验收。

## 4. 按改动范围验证

| 改动位置 | 首选测试 |
| --- | --- |
| API、schema、鉴权、接入 | `tests/test_add_api.py`、`tests/test_read_api.py`、`tests/test_add_agent.py` |
| 抽取、输入预算、模型输出 | `tests/test_add_worker.py`、`tests/test_extraction_input.py`、`tests/test_model_input.py`、`tests/test_providers.py` |
| 队列、租约、并发 | `tests/test_task_queue.py`、相关 Worker 测试 |
| 数据约束、证据、生命周期、TTL | `tests/test_schema_constraints.py`、`tests/test_lifecycle_cases.py`、`tests/test_memory_management.py`、`tests/test_ttl.py` |
| 检索和向量 | `tests/test_retrieval.py`、`tests/test_read_api.py`、`tests/test_governance_worker.py` |
| 治理、画像 | `tests/test_consolidation.py`、`tests/test_profile.py`、`tests/test_profile_config.py` |
| Honcho 迁移 | `tests/test_honcho_migration.py`、迁移工具的 dry-run/对账步骤 |

示例：

```bash
poetry run pytest -q tests/test_add_api.py tests/test_add_worker.py
poetry run ruff check src tests
git diff --check
```

涉及数据库结构时，先在独立测试库运行 `poetry run alembic upgrade head`，再跑相关 schema/迁移测试；可使用 `poetry run alembic check` 检查 ORM 与迁移漂移，但已有迁移与 ORM 之间可能存在历史漂移，需对照当前结果定位。`scripts/run_validation.sh` 是较广的验证脚本，会执行全量测试、迁移和报告写入，不能当作只读快捷检查，也不应直接用于业务库。

## 5. 交接开发时的最小检查清单

- 改 API：更新请求/响应模型、对接说明和专项 API 测试。
- 改记忆状态或证据：检查写入、读取、下游传播、向量维护、审计和迁移约束。
- 改异步任务：检查幂等键、租约失效、失败重试、部分提交与任务可观察结果。
- 改模型提示词/筛选：使用现有 `scripts/evaluate_*.py` 和样本评估；记录模型、样本、结果与限制。
- 记录验证：写清运行命令、环境、通过项和未通过项。`reports/` 里的既有数字只代表生成当时的快照。

复杂数据库改动和真实模型评估步骤分别参考 [数据模型设计规范](统一记忆服务数据模型详细设计规范-V1.0-冻结版.md)与现有 `reports/` 记录；当前实现仍以代码和迁移为准。
