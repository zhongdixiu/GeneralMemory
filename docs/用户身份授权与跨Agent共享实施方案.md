# 用户身份授权与跨 Agent 共享实施方案

> 2026-10-12 状态补充：Add 的会话／来源 Agent 隔离和按用户划分的请求幂等已在核心优化中实现，见 [ADD 接口运行说明](./ADD接口运行说明.md)。本文此前将这些调整列为后续工作的描述属于原阶段记录；公司真实用户鉴权、可信身份绑定及同用户跨 Agent 回执授权仍暂缓，当前任务查询仍按静态凭证的租户和调用 Agent 限制。

日期：2026-10-10。

状态：首版共享规则已由用户确认。公司鉴权接入暂缓，保留现有静态服务凭证；Search 和独立 Profile 的代码已落地，验证记录见后续开发计划及接口运行说明。下文公司 user token 改造为后续方案，不是当前已实现能力。

## 1. 已确认的首版规则

- 普通用户接口使用公司 user token，用户身份来自可信验证结果。
- 同一租户内，同一用户在不同 Agent 中产生的事实、推断及画像默认共享。
- 不允许访问其他用户或其他租户的个人记忆。
- agent_id 是调用方自报的来源标识，首版不据此授予权限，也不按 Agent 来源限制个人记忆读取。
- 全部共享表示可访问；检索仍执行任务适用性、状态、有效期及依据有效性检查。
- 治理管理、审计内容读取和公共记忆发布权限独立，不由普通 user token 或自报 agent_id 自动获得。
- 首版不实现 Agent 授权表、授权界面或分 Agent 访问控制。
- 用户已确认：画像由独立的 Profile 接口读取，并默认返回用户全部有效画像、保留适用条件；Search 返回相关事实和推断，不合并画像。当前接口契约见[Search 与 Profile 运行说明](./Search与Profile接口运行说明.md)。

### 当前联调阶段的临时接入方式

- 2026-10-16 配置收敛：部署仅保留业务 Agent 凭证，在同一凭证上配置 can_manage_memories、can_manage_governance、can_read_audit_content 三个默认关闭的能力开关，不要求独立治理 token，不新增角色或授权表；后续仍由独立授权控制面接管。审计内容开关可独立授予审计读取，不要求治理权限。

- 保留现有 StaticCredentialStore：凭证固定 tenant_id、caller_agent_id；Add 的来源允许列表和管理权限继续执行。
- user_id 暂由受信任的接入后端提供，尚未与公司登录用户核验。普通请求不接受客户端自行选择其他租户；当前租户来自静态凭证。
- 后续 Search、Profile 按凭证租户和请求指定用户限定个人记忆，默认可读取同用户来自不同 Agent 的有效记忆；不能因为共享而扩大到其他用户、Agent 自身记忆或未经授权的组织记忆。
- 当前 Search 支持可选 agent_id、source_system 来源过滤，不据此授予权限，也不增加 session_id。agent_id 匹配来源当前版本的可追溯提交及来源 agent_id，Add 核心升级后的完整证据组可包含同 Agent 的必要 history 来源，该值可由 Add 自报，省略时取凭证 caller_agent_id；不使用 created_by 或消息作者猜测来源 Agent。事实和推断都须有至少一组完整有效依据全部落在筛选范围，详见接口运行说明。可信调用身份仍保存在 caller_agent_id，自报来源不能替代凭证身份。
- 现有 Add 和任务查询行为本轮不变：任务回执仍按租户、调用 Agent 检查。改为同用户跨 Agent 查询回执的代码调整尚未实施，不把它作为已有能力。
- 临时方式仅用于受信任后端接入与联调。它能够验证指定用户的跨 Agent 共享，不能证明实际调用者就是该用户；公司鉴权接入前，不能宣称已具备登录用户级访问保护。
- 不因暂缓公司鉴权而移除现有认证、接收任意自报租户或开放管理接口。当前普通入口不新增公司凭证模拟协议或 Agent 授权框架。

## 2. 后续接入公司鉴权前必须明确的信息

### 公司 user token 验证

需要已有验证接口的 URL、HTTP 方法、token 传递方式，以及成功、无效或过期时的脱敏响应示例；不需要真实 token。

已知验证结果只能返回用户身份。因此不能假定 token 包含 tenant_id 或可信应用身份，也不能自行约定公司的字段、响应格式或用户 ID 映射。还需确认公司允许该 token 用于记忆服务。

用户随后提供了图片生成接口的调用示例：请求使用 `Authorization: Basic <credential>`，并携带 `x-yun-api-version: v1`。示例没有用户身份验证响应，不能据此确定凭证内部格式、验证方法、统一用户 ID 或租户关系。应按公司的实际 Basic 凭证协议接入，不能沿用此前假定的 Bearer 格式；仅解码凭证不能替代验证。图片生成接口不是已确认的身份验证入口，不能用业务调用探测凭证有效性。本方案不保存示例中的原始凭证。

### 租户确定

选择实际部署需要的方式：

- 单租户：由服务端固定 tenant_id；确认哪些公司用户可接入这一租户。
- 多租户：请求可以选择 tenant_id，但必须由可信外部目录或服务端维护的关系核验该用户是否有权访问。

不能仅凭调用方传入 tenant_id 授予访问权限。本轮尚未选择其中一种方式，不提前建设租户主数据系统。

## 3. 必要代码改造

| 范围 | 现状 | 改造目标 |
| --- | --- | --- |
| auth.py、settings.py | 静态服务 token 映射租户、Agent 和权限，没有当前用户身份 | 接入公司 token 验证；普通请求取得可信 user_id 及经过确定/核验的租户；Agent 保留来源语义 |
| api_schemas.py、api.py | Add 的 user_id 由正文提供，来源 agent_id 可自报，caller_agent_id 由服务凭证提供 | 明确来源 Agent 的传递方式；保留现有 user_id 时必须与认证结果一致；在接入及幂等重放前完成检查 |
| api.py 的任务查询 | 按 tenant_id、caller_agent_id 限制 | 用户入口按 tenant_id、已认证 user_id 及可公开的任务类别限制；不同 Agent 可读取同用户的 Add 回执，不能因此开放内部治理任务 |
| ingest.py 的来源记录 | 用户消息的 author_id 是用户，source_system 是来源系统；接入来源 agent_id 与凭证 caller_agent_id 分别记录在每条来源上 | 明确记录来源的接入 Agent；不能把消息作者或 source_system 自动当成接入 Agent；同一来源被重复接入时不能覆盖原始来源信息 |
| ingest.py、models.py 的 Add 幂等 | 范围为 tenant_id、caller_agent_id、Idempotency-Key | 用户请求的幂等身份包含 tenant_id、user_id、来源 Agent、客户端幂等键；查询、锁和唯一性保持一致；兼容已有任务，不统一改写后台任务规则 |
| retrieval.py、profile.py | 用户记忆和画像已按租户、用户归属 | 复用现有逻辑；未来公开入口只传入经过认证与核验的主体，不接受客户端指定额外授权主体 |

用户事实仍使用 subject_type=user、subject_id=user_id。subject_type=agent 表示 Agent 自身记忆，不能用来存储“某用户在某 Agent 中产生的记忆”。

核心记忆归属不需要重建；Add 幂等唯一性调整是否需要 migration，应在具体实现时核对既有约束、队列入口及存量兼容后确定。

## 4. 用户入口与管理入口

普通 Add、任务查询及后续 Search、Profile 统一使用用户授权边界。静态服务凭证可继续用于已授权的治理管理与后台接入；不能在公司 user token 验证失败后回退为更宽的普通用户访问权限。

公司鉴权不可用与 token 无效应当区分，均不能放行。原始 user token 不写入来源、任务 payload、审计或错误响应。

本批先完成用户鉴权和现有 Add/任务入口改造。公开 Search、Profile 的请求与响应协议后续逐项讨论，未因确认授权规则而视为已冻结。

## 5. 实施顺序与验收

公司鉴权接入暂缓期间，先逐项确认 Search、Profile 请求与响应契约，再使用上面的临时接入方式实现读取闭环。下列身份绑定、跨 Agent 回执和用户幂等调整留到恢复鉴权改造时实施；现有未改造接口不视为通过这些验收。

1. 接入 user token 验证及租户确定 → 验证有效身份可用、无效身份被拒绝、鉴权不可用不放行。
2. 改造 Add、任务访问、来源及幂等 → 验证同用户跨 Agent 回执可读、来源可追溯、不同用户幂等互不冲突、同请求重放行为保持。
3. 运行相关回归和静态检查 → 验证跨用户、跨租户访问被拒绝，治理与审计权限不扩大，既有 Worker 行为保持。

关键验收案例：

- token 属于 user1，Add 正文却指定 user2：拒绝且不写入，不重放其他用户任务。
- user1 通过 Agent A 提交，通过 Agent B 查询自己的 Add 回执：允许。
- user2 查询 user1 的 Add 回执：拒绝。
- 请求未经授权的租户：拒绝；单租户部署不能通过请求选择其他租户。
- 同 Agent、不同用户使用相同客户端幂等键：互不冲突且不共享任务。
- 同租户、同用户、同来源 Agent 重放同一请求：返回原任务，不重复写入；相同键不同请求仍冲突。
- 自报管理员 Agent ID：不能获得治理管理或审计内容权限。
- 用户鉴权超时、服务异常或返回非法身份：不创建任务、不返回记忆内容。

## 6. 后续按 Agent 授权的边界

未来需要可信的调用应用身份、用户授权记录，以及对事实、合并、纠正、推断及其依据的访问规则。created_by 只表达创建者，不能替代多来源证据关系。

首版自报的 Agent 来源不是已认证来源，未来启用限制时需明确历史数据的处理方式。默认共享画像也不自动开放画像依据的原始内容；如未来画像本身需要按来源隔离，需另行设计。

首版保留来源和证据关系，不预先实现上述权限功能。
