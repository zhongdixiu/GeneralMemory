# 模块开发指南

本页按运行职责解释代码。阅读一个模块时，先看“入口和产出”，再看“处理逻辑”，最后看关联测试。文件是协作边界的线索，实际跨模块契约主要是 `memory_task`、`memory_item`、`memory_evidence` 和 API schema。

## 1. API、鉴权与请求模型

**入口与产出：** `server.py` 启动 `api.create_app()`；`api.py` 注册所有 `/api/v1` 路由；`api_schemas.py` 定义请求和响应。API 做校验、鉴权、事务组织与错误映射，耗时抽取交由任务处理。

**主要逻辑：** `settings.py` 从环境变量装载数据库、静态凭证、模型端点和预算。`auth.py` 将 Bearer token 的哈希映射到租户、调用 Agent、可写来源以及三个可选能力：`can_manage_memories`、`can_manage_governance`、`can_read_audit_content`。API 不接受客户端自报租户。中间件生成或接收 `X-Request-ID`，对 POST/PUT 请求限制 2 MiB，并将请求 ID 回传。Pydantic 拒绝多余字段和显式 `null`；不同路由按能力检查权限。

**改动影响：** 新增字段需同时检查 schema、入库映射、幂等指纹、任务结果、接口说明和 API 测试。鉴权改动须覆盖跨租户、来源写入范围与审计正文隔离。用户身份认证尚未在本服务中实现；调用方必须是受信任后端。

**测试：** `test_add_api.py`、`test_read_api.py`、`test_memory_management.py`、`test_audit.py`、`test_profile_config.py`。

## 2. 接入和来源管理

**入口与产出：** `ingest.ingest_and_enqueue()` 接收合法 Add 请求，在一个事务中创建 `source_record`、`conversation_session` 批次号、`memory_task(fact_extract)`、`memory_task_source` 关联和审计；返回任务 ID。

**主要逻辑：** 幂等键按租户、调用 Agent、来源 Agent 和用户限定，配合请求指纹防止同键不同内容。原始消息按来源系统、会话和 `message_id` 绑定；同 ID 不同语义输入报冲突。`messages` 是本次目标，`history_messages` 只供上下文使用；历史消息本身不因作为 history 提交而独立形成事实。接入会保存作者、原始时间、接收时间和时间来源，且在同会话中分配递增 `batch_seq`。重复来源的有效版本复用，失效来源不能直接重用。

**与下游的约定：** Add Worker 从 `memory_task_source` 读取目标与历史及来源版本。外部来源被纠正或失效时，需要经过 `lifecycle.py` 和维护任务传播，而不是直接覆写来源正文。

**测试：** `test_add_api.py`、`test_add_context.py`、`test_add_agent.py`、`test_add_time_semantics.py`。

## 3. 任务队列与事实抽取

**入口与产出：** `worker.run_once()` 领取 `fact_extract`；`worker._process_task()` 把目标消息转为事实记忆、证据和处理结果。`task_queue.py` 是各 Worker 共用的入队、领取、租约续期、结束与重试层。

**处理顺序：**

1. `task_queue.claim_tasks()` 使用数据库行锁和租约领取任务；同一来源会话中较早的批次未结束时，较晚批次不能先处理。Worker 处理过程中续租，并在提交前检查租约令牌。
2. `_load_task_input()` 校验当前来源和任务关联，读取目标、可用历史及相关记忆；`extraction_input.py` 根据输入/输出预算组成切片，保留必要的上下文依赖。
3. `providers.QwenFactModel` 返回候选事实及处理结论；`providers.py` 校验证据、候选跳过原因和模型结构；`business_scenes.py` 规范业务场景。输出截断时，Worker 可将切片继续拆分。
4. SiliconFlow 为接受的候选生成 embedding；`_plan_decisions()` 用相似候选和模型判断新增、重复、纠正等处理；`_commit_results()` 分片提交事实、证据和结果。
5. 执行进度保存在任务 `payload.execution`，重试从持久化进度继续。已提交分片若后续失败，任务可能为 `partial`，不能按“完全未写入”处理。

**关键约束：** 模型输出不是可信数据。事实必须通过目标/历史依据校验、范围与时间校验、来源版本复核；向量相似度只用于路由候选，不直接决定丢弃事实。任务有模型调用预算，越限会失败或进入部分完成。生产模型调用放在数据库事务外的阶段，最终写入前复核输入和租约。

**测试：** `test_add_worker.py`、`test_extraction_input.py`、`test_model_input.py`、`test_fact_governance.py`、`test_providers.py`、`test_task_queue.py`。

## 4. 数据、证据与记忆生命周期

**文件：** `models.py` 定义 ORM 和约束；`repositories.py` 写入来源、事实、画像和证据组；`evidence.py` 判断依据是否完整有效；`lifecycle.py` 处理更新、删除、失效、到期与下游传播；`ttl.py` 计算保留期限。

**证据规则：** `supports` 从来源到事实，`derives` 从事实到推断，`profile_basis` 从记忆到画像。每条边记录上游版本，因而来源或事实更新后，旧边不会自动证明新版本。一个证据组要求组内全部依据有效；一个对象可以由任一完整独立组支持。读取端复核这些条件，不等待后台依赖复查完成。

**状态规则：** 记忆可以是 `active`、`disputed`、`invalidated`、`expired`、`deleted`。修改事实会创建新事实并使旧事实失效，不原地重写旧正文；删除为逻辑删除，不物理清除来源。TTL 到期与删除都会让下游失去相应支持，并安排向量删除、画像更新或依赖复查。版本变化、有效时间和证据状态会影响检索可见性。

**改动影响：** 变更状态或证据关系时，同时检查 `models.py` 约束、Alembic 迁移、`evidence.py`、`retrieval.py`、`profile.py`、维护任务和审计。不能只修改写入路径。

**测试：** `test_lifecycle_cases.py`、`test_memory_management.py`、`test_schema_constraints.py`、`test_ttl.py`、`test_retrieval.py`。

## 5. 检索与向量维护

**入口与产出：** HTTP Search 由 `api.py` 调用 `retrieval.search_task_memories()`，只返回可用的用户事实/推断及其认知类型。内部还有 `search_memories()`，用于显式业务范围的检索场景。`governance_worker.py` 的 maintenance 角色处理 `vector_upsert`、`vector_delete`、`ttl_expire`、`dependency_recheck`。

**主要逻辑：** Search 先根据租户、用户、状态、生效时间、TTL 和范围限制候选；再使用 query embedding 和 pgvector 召回。可选 `use_model=true` 时，由模型选出更适合当前任务的候选。传入 `agent_id`、`source_system` 时，过滤的是事实的真实来源证据，推断需要完整的上游事实来源满足条件。返回前再次验证当前向量模型/正文、证据与版本，避免旧向量泄漏失效记忆。

**维护逻辑：** Add Worker 在新事实提交时写入向量；后续内容变化产生的向量任务带目标版本和正文哈希，维护 Worker 在提交时拒绝过时任务。到期扫描只把需要处理的有效记忆入队；向量更新、删除和下游复查分开执行，API 不等待其物理完成。

**测试：** `test_retrieval.py`、`test_read_api.py`、`test_governance_worker.py`、`test_add_agent.py`、`test_ttl.py`。

## 6. 治理、争议与推断

**入口与产出：** `governance_state.py` 管理租户策略、用户变更状态和任务触发；`consolidation.py` 消费 `consolidate` 任务，记录 `governance_operation`，可能合并记忆、标记/解决争议、生成或复核推断。管理 API 提供策略、运行、争议和撤销入口。

**主要逻辑：** 事实变更标记用户待整理；手动触发可直接创建运行，自动整理受策略开关和阈值/等待时间控制。运行按用户范围取快照，模型给出建议后，代码复核范围、时间、证据充分性、当前版本和任务租约，再提交变更。推断只从满足独立性与证据要求的事实形成，不以推断继续推断；争议组需要整体复核。操作保留可审阅信息，撤销时再次检查版本，不能无条件回滚后续修改。

**边界：** 治理与 Add 是不同 Worker；只运行 API 或 Add Worker 不会执行整理。自动运行默认策略需显式启用。模型建议可能被代码拒绝或跳过，运行记录与最终记忆状态应一起查看。

**测试：** `test_consolidation.py`、`test_governance_optimization.py`、`test_business_scenes.py`、`test_fact_governance.py`。

## 7. 画像与维度配置

**入口与产出：** `profile_config.py` 管理租户的画像维度列表和版本；`profile.py` 合并 `profile_rebuild` 请求、选取有效记忆、调用画像模型、验证精确引用并写入独立画像陈述。Profile Worker 还消费 `profile_config_apply`，逐批为受影响用户安排重建。

**主要逻辑：** 明确画像从有效、具有长期价值且非项目限定的用户事实生成；推断画像由配置开关 `MEMORY_PROFILE_ALLOW_INFERRED` 控制，读取还需 `include_inferred=true`。模型输出须引用现有记忆 ID 和原文片段，且维度 key 必须已启用。一个维度允许多条陈述；配置变更增加版本，旧版本画像在新配置应用前不输出。新候选经过短暂合并窗口再重建，来源失效或证据变化会立即阻断旧画像读取。

**边界：** GET `/profiles` 只读，不实时调用模型；手动 `/profiles/rebuild` 绕过等待但仍通过任务执行。改维度描述会影响模型分类和重建范围，需检查租户配置版本与画像迁移。

**测试：** `test_profile.py`、`test_profile_config.py`、`test_profile_migration.py`、`test_read_api.py`。

## 8. 审计、历史迁移与辅助工具

**审计：** `audit.record_audit()` 与业务变更处于同一事务，将目标、操作、原因、操作者和前后状态写入 `memory_audit_log`；`list_audits()` 提供按目标、任务和关联 ID 查询。审计元信息与内容详情受不同权限控制。ORM 阻止修改/删除审计行；数据库级只追加还依赖运行账号权限配置。

**历史迁移：** `migration_tools/honcho/` 包含源库只读读取、画像统计、批次选择、映射、写入和对账。`scene_migration.py` 与 `scripts/migrate_business_scenes.py` 负责存量业务场景规范化。`migrations/versions/` 是服务自身表结构升级，与数据迁移工具用途不同。

**辅助：** `smoke_data.py`、`fixture_loader.py`、`retrieval_smoke.py`、`scripts/evaluate_*.py` 用于样本构建、评估和验证；`reports/` 存放既有结果，不能据此推断当前分支或真实模型质量。

**测试：** `test_audit.py`、`test_honcho_migration.py`、`test_add_migration.py`、`test_business_scenes.py`。

## 其他入口文件速查

| 文件 | 什么时候需要看 |
| --- | --- |
| `db.py` | 调整 SQLAlchemy engine 创建或数据库连接配置 |
| `task_results.py` | 调整 Add 任务对外状态或结果格式；内部 `processing` 在 HTTP 响应中映射为 `pending` |
| `model_input.py` | 修改提交给事实抽取/治理模型的紧凑输入结构与大小估算 |
| `add_management.py` | 管理员受控重处理已结束的 Add 任务及原来源 |
| `deterministic_embedding.py` | 测试或本地验证中需要确定性向量替身 |
| `fixture_loader.py`、`smoke_data.py` | 导入生命周期样本或生成检索性能样本 |
| `retrieval_smoke.py` | 查看检索查询计划和样本性能指标 |
| `scene_migration.py` | 审查、应用存量业务场景标签迁移报告 |

Honcho 子包按 `source.py`（源库只读扫描和批次选择）→ `migration.py`（目标库映射、写入及对账）→ `profile.py`、`migrate.py`、`validate.py`（三个命令入口）阅读；`cli.py` 负责公共参数与连接配置。
