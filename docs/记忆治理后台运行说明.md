# 手动运行和验证记忆治理

这份说明带你从启动服务开始，手动发起一次记忆整理，并查看整理结果。命令默认在项目根目录执行，示例地址为 `http://localhost:8000`。

## 先理解要启动什么

记忆治理分成两类后台工作：

- `maintenance` 定期检查到期记忆、失效来源和需要重建的向量。服务启动后它会自己扫描，不需要手动发起整理。
- `consolidation` 等待管理接口创建整理任务，再用模型检查跨会话记忆是否需要合并、推断或标记失效。

只有 API 在运行时，任务不会自动被处理。下面会启动 API 和三个 Worker。每个命令都要在一个单独的终端窗口运行，并保持窗口开启。

## 第一步：配置并启动服务

先按项目的 [`.env.example`](../.env.example) 配好数据库、模型服务和凭证。不要把真实密码或 API Key 写进文档或提交到 Git。至少需要：

- `MEMORY_DATABASE_URL`：数据库连接地址。
- `MEMORY_AUTH_CREDENTIALS_JSON`：API 调用凭证，下面会讲管理凭证。
- `DASHSCOPE_API_KEY`：Add 和整理任务调用模型时使用。
- `SILICONFLOW_API_KEY`：Add 和维护任务生成向量时使用。

载入 `.env`，安装依赖并更新数据库表结构：

```bash
set -a
source .env
set +a
poetry install
poetry run alembic upgrade head
```

升级到 `0004_business_scenes` 后，先让已开始的旧版本 Add/整理任务结束，再启动新 Worker。存量场景只生成报告时执行 `poetry run python scripts/migrate_business_scenes.py`，默认写入 `/tmp/memory_cmic_business_scene_migration.jsonl`；可用 `--tenant-id` 和 `--report` 指定范围与路径。逐条核对完整正文和报告中的来源，编辑 `proposed`、`reason`，为新场景补 `definitions`；多标签归一时在 `label_map` 中逐项注明旧名到新名的对应关系。只有确认旧名在本租户没有其他含义时，才把它加入 `register_aliases`；同名异义旧值不能登记为全租户别名。不确定的记录保留 `proposed: null`。复核后执行 `poetry run python scripts/migrate_business_scenes.py --apply <报告路径>`。应用时会复核版本、状态和旧范围；画像唯一键碰撞、输入变化及未解决项逐条报告，不自动改写。重复应用同一报告不会重复变更。

内部任务查询使用 `memory_cmic.retrieval.search_task_memories`，传入 query、租户与可信主体、向量模型和适用性模型；调用方不需提供业务标签。现有 `search_memories` 保留显式范围调用。新入口抛出 `ProviderError` 时应向调用链报告，不降级为标签精确匹配。

下面四条命令分别在四个终端窗口执行：

**终端 1：API**

```bash
set -a && source .env && set +a
poetry run memory-cmic-api
```

**终端 2：接收新记忆的 Add Worker**

```bash
set -a && source .env && set +a
poetry run memory-cmic-worker --role add
```

**终端 3：定期维护 Worker**

```bash
set -a && source .env && set +a
poetry run memory-cmic-worker --role maintenance
```

**终端 4：处理手动整理任务的 Worker**

```bash
set -a && source .env && set +a
poetry run memory-cmic-worker --role consolidation
```

看到各进程没有退出并持续运行，就先保持它们开着。若只想验证手动整理，并且数据库里已经有记忆，实际必需的是 API 和 `consolidation` Worker；Add Worker 用于本教程下一步创建示例记忆，maintenance Worker 负责到期和派生清理。

## 第二步：准备管理凭证

治理接口只允许带有 `can_manage_governance: true` 的凭证访问。编辑 `.env` 里的 `MEMORY_AUTH_CREDENTIALS_JSON`，在凭证数组中加入一个管理凭证。示例中的 token 仅为占位内容，请换成自己的随机值：

```dotenv
MEMORY_AUTH_CREDENTIALS_JSON='[
  {"token":"替换成自己的随机管理token","tenant_id":"tenant_demo","caller_agent_id":"governance_admin","can_manage_governance":true},
  {"token":"替换成自己的随机接入token","tenant_id":"tenant_demo","caller_agent_id":"demo_agent","allowed_source_systems":["demo"]}
]'
```

两个凭证必须使用同一个 `tenant_id`：第一个用于治理管理，第二个用于发送 Add 请求。管理凭证不需要 `allowed_source_systems`。改完 `.env` 后，重启 API 和 Worker 让它们读取新配置。

在**新的终端**中设置后续命令使用的示例变量。这里的 token 和用户 ID 要与你自己的 `.env` 和数据一致：

```bash
export API=http://localhost:8000
export ADMIN_TOKEN='替换成自己的随机管理token'
export ADD_TOKEN='替换成自己的随机接入token'
export USER_ID='governance_demo_user'
```

检查管理接口是否可用：

```bash
curl "$API/api/v1/governance/policy" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

成功时会返回本租户策略，例如 `auto_enabled`、`min_changed_memories` 和 `cooldown_minutes`。首次使用时，自动整理默认关闭；这不影响下面的手动触发。

如果返回 `401`，检查 token 是否与 `.env` 完全相同；如果返回 `403`，检查该凭证是否包含 `can_manage_governance: true`，并确认修改配置后重启了 API。

## 第三步：准备可整理的记忆

治理按“租户 + 用户”处理记忆。若数据库中已经有目标用户的记忆，可以跳到下一步。否则，用 Add 接口放入两条不同会话里的相关事实。把 `USER_ID` 换成后续治理时要用的用户 ID：

```bash
curl -X POST "$API/api/v1/memories:add" \
  -H "Authorization: Bearer $ADD_TOKEN" \
  -H 'Idempotency-Key: governance-demo-1' \
  -H 'Content-Type: application/json' \
  -d "{
    \"source_system\": \"demo\",
    \"user_id\": \"$USER_ID\",
    \"session_id\": \"report-session-1\",
    \"messages\": [{
      \"message_id\": \"report-message-1\",
      \"role\": \"user\",
      \"content\": \"写项目周报时，请先写结论，再列出依据。\",
      \"occurred_at\": \"2026-09-28T10:00:00+08:00\"
    }]
  }"
```

再发送另一条不同会话的相关事实（使用新的幂等键、会话 ID、消息 ID 和时间）：

```bash
curl -X POST "$API/api/v1/memories:add" \
  -H "Authorization: Bearer $ADD_TOKEN" \
  -H 'Idempotency-Key: governance-demo-2' \
  -H 'Content-Type: application/json' \
  -d "{
    \"source_system\": \"demo\",
    \"user_id\": \"$USER_ID\",
    \"session_id\": \"report-session-2\",
    \"messages\": [{
      \"message_id\": \"report-message-2\",
      \"role\": \"user\",
      \"content\": \"整理项目复盘时，希望先给结论，再补充原因和细节。\",
      \"occurred_at\": \"2026-09-28T11:00:00+08:00\"
    }]
  }"
```

Add 通常先返回 `202` 和任务 ID，表示请求已排队，不代表记忆已经写入。用 Add 凭证和返回的 ID 查询任务：

```bash
curl "$API/api/v1/tasks/<add_task_id>" \
  -H "Authorization: Bearer $ADD_TOKEN"
```

重复查询，直到状态为 `succeeded`，再触发治理。若没有等待 Add 任务结束，治理可能先于记忆入库执行。

## 第四步：手动触发整理

发起一次针对该用户的整理任务：

```bash
curl -X POST "$API/api/v1/governance/runs" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Idempotency-Key: governance-run-1' \
  -H 'Content-Type: application/json' \
  -d "{\"user_id\":\"$USER_ID\"}"
```

记下返回内容里的 `task_id`。例如：

```json
{
  "task_id": "返回的任务ID",
  "user_id": "governance_demo_user",
  "status": "pending",
  "automatic": false
}
```

`automatic: false` 表示这是你手动触发的任务。即使自动整理策略关闭，管理接口也可以手动创建任务。同一个用户若已有排队或运行中的任务，服务可能返回已有任务；相同的 `Idempotency-Key` 重试也会返回原任务。

## 第五步：查看任务有没有完成

将下面的 `<task_id>` 替换为上一步返回的 ID：

```bash
curl "$API/api/v1/governance/runs/<task_id>" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

刚触发时状态可能是 `pending`。几秒后重复运行查询命令，直到看到终态：

- `succeeded`：任务正常完成。
- `partial`：本轮完成了部分工作，仍有记忆留待后续处理。
- `failed`：任务失败；查看返回的 `error` 字段和 Worker 终端日志。

如果状态一直是 `pending`，通常是 `consolidation` Worker 没启动、连接了不同的数据库，或 Worker 配置没有载入。检查终端 4 和 `MEMORY_DATABASE_URL`。

## 第六步：查看整理做了什么

查询本任务逐项操作：

```bash
curl "$API/api/v1/governance/runs/<task_id>/operations" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

重点看 `operations` 数组里的 `kind`、`memory_id` 和 `details`。数组有内容表示治理留下了具体操作记录，例如合并、推断或失效处理；每条记录会说明涉及的记忆和操作依据。

如果 `operations` 是空数组，也可能是正常结果：例如目标用户还没有两条适用范围相同、来自不同会话的有效事实，或模型判断现有事实不需要修改。检查任务详情中的 `selected`、`processed`、`remaining` 和 `results`，确认是否选中了记忆、是否处理完成。治理有意采取保守策略，不保证每次运行都会产生改动。

## 自动运行（可选）

手动流程确认正常后，才需要开启后台自动整理。查看当前策略：

```bash
curl "$API/api/v1/governance/policy" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

开启自动整理：

```bash
curl -X PATCH "$API/api/v1/governance/policy" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"auto_enabled":true}'
```

自动整理由 `consolidation` Worker 按策略检查，不代表每次扫描都会调用模型。默认需要至少 5 条变化，且用户空闲 10 分钟；另有冷却时间和最长等待时间。查询策略响应可查看当前具体数值。关闭自动整理：

```bash
curl -X PATCH "$API/api/v1/governance/policy" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"auto_enabled":false}'
```

## 常见问题

| 现象 | 检查方法 |
| --- | --- |
| `401` 未认证 | token 是否和 `.env` 中完全一致；改过 `.env` 后是否重启服务。 |
| `403` 无权访问 | 管理凭证是否设置了 `can_manage_governance: true`。 |
| Add 返回 `403` | Add 凭证的 `allowed_source_systems` 是否包含请求里的 `source_system`（示例为 `demo`）。 |
| 整理任务一直 `pending` | `consolidation` Worker 是否运行；API 和 Worker 是否使用同一个数据库。 |
| 任务成功但没有操作记录 | 可能没有合适的记忆候选，也可能模型判定不应更改；先看任务 `selected` 和 `results`。 |
| Add 任务未完成就触发整理 | 等 Add Worker 处理完成后，再创建治理任务。 |

手动触发治理不会立即扫描或清理到期记忆；到期记忆和派生数据由持续运行的 `maintenance` Worker 负责。
