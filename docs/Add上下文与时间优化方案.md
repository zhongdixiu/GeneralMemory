# Add 上下文与时间优化方案

日期：2026-10-13。本文汇总本轮已确认的业务规则和建议实施方式。本轮已在工作区实施并加入迁移与回归；尚未迁移业务数据库或重启服务。排查证据见 [动物园案例](../reports/add_zoo_context_diagnosis.md)、[outcome 审查](../reports/add_outcome_time_review.md)、[时间链路审查](../reports/add_time_semantics_review.md)。本方案中的新规则优先于这些报告对旧行为的描述。

## 1. 目标与范围

目标：Add 可以理解连续消息，维护已有计划和事实；消息时间、事件时间、记忆生效和保留期限各自明确；今天首次告知的过去事实可以从今天开始记住，不会因为事件发生在过去而刚导入就过期。

本轮保留既有来源、证据、任务冻结、切片与治理架构；保留同会话最近 30 条普通消息的历史窗口。不是最近 30 天，也不保证 30 条全部能放进模型输入。必要回复/回合/工具关联仍可超出普通窗口寻找。

本轮不全面重做超长上下文，不引入无限自动恢复，不自动重新激活所有存量过期记忆。跨会话原文证据的自动读取涉及现有命名空间校验，分后续阶段处理；本轮先完成同会话更新链路。

## 2. 已确认的时间语义

| 概念 | 新规则 | 不承担的职责 |
| --- | --- | --- |
| 消息来源时间 occurred_at | 用户何时发送/声明这句话；解释相对日期、判断声明先后 | 不等于正文中的事件日期，不决定首次导入是否已经忘记 |
| 首次接收时间 received_at | API 首次接受此来源的服务端时间，保存后不随重试变化 | 不冒充未知历史消息的真实发送日期 |
| 记忆生效时间 effective_at | 这条记忆从何时开始对外可用，必须 >= 来源首次接收时间 | 不表示过去经历的实际起点或未来计划的执行日期 |
| 事件/经历日期 | 补全在自足的记忆正文，保留日期粒度和条件 | 不直接作为记忆生效日、保留截止 |
| 记忆到期时间 expired_at | 按分类默认计算，或采用用户明确的记忆保存期限 | 不自动等于过去事件结束或过去状态区间结束 |
| temporal_kind | current / historical，描述内容的时间性质 | 不表达 active/expired 等系统状态 |
| status | active / invalidated / disputed / expired，表达记忆生命周期 | 不代表正文所述事件目前仍在发生 |

北京时间统一采用 Asia/Shanghai。无时区的完整日期时间按北京时间解释；已带时区的输入先按真实时间转换至北京时间，不能直接替换偏移。数据库可以继续存 UTC。

### 2.1 生效和默认保留期限

```text
未明确未来才开始适用：effective_at = 首次接收时间
明确未来才开始适用：effective_at = max(首次接收时间, 明确适用起点)

temporary：expired_at = effective_at + 30 天
regular：expired_at = effective_at + 180 天
long_term：无默认到期时间
```

对于多个目标共同形成的事实，采用被引用目标消息的首次接收时间最大值；不使用辅助历史的旧接收日期来提前新事实的保留期。后台晚执行或任务重试不更新 received_at。

“用户2024年在北京居住过”今天首次告知，应 historical + regular + active，从今天开始默认保留 180 天。没有居住起止日期同样保存。historical 不再要求完整区间，也不会自动写 expired。

重复提交相同来源不续期；重复事实仅补证据，也继续沿用当前不续期策略。若用户明确更正事实或改变保存期限，则作为对应更新处理，不能把幂等重放当成续期。

### 2.2 时间信息进入哪个位置

| 用户表达 | 如何处理 |
| --- | --- |
| 我2024年在北京住过 | 经历年份保留在正文；historical；常规保留期从首次接收起算 |
| 这周六带儿子去动物园玩一天 | 解析具体日期并补进正文；计划现在可用，不等到周六才生效 |
| 下月1日起，周报采用列表 | 正文保留未来适用条件；effective_at 为下月1日，且不早于接收时间 |
| 这个工作安排月底结束 | 正文保留适用截止；不能月底之后继续当作当前安排使用；该事实的系统保留期限独立计算 |
| 这条记忆只保存一个月 | 识别为明确记忆保存期限，覆盖默认 TTL |

规则/计划的适用截止与系统保留期分开。用户提供的日期必须被利用，但须根据语义进入正确位置。“活动去年结束”是今天可记住的历史事实，不能因此写 expired_at=去年。

本轮优先把事件日期、适用区间写清楚在正文，并让 Search 的语义适用性判断保留/检查这些条件；不新增通用事件时间表或自动推断事件已执行的定时流程。计划在事件之后仍可作为过去计划的记录，不得当成已执行或仍待执行的事实。必要的结构化适用区间可以后续按真实场景增加，不能复用 expired_at 来替代。

## 3. 时间接入与友好输入

### 3.1 建议的请求契约

不新增请求级接入模式。普通 Agent 按既有 messages/history_messages 接口提交，服务根据每条消息的来源时间、是否显式标记时间未知和消息位置处理。一次请求可混合已知日期的旧消息和实时消息，不能用一个请求级开关统一决定。

普通业务 Agent 通常能从会话记录取得用户发送时间，应直接传 occurred_at，timestamp_origin 使用默认 source。这里的“导入适配程序”只是调用 Add 的接入代码，例如读取旧聊天文件的脚本，不是当前服务要求新增的一套组件或接入模式。

改动前已有 adapter_observed 的含义是：调用方不知道原消息发送时间，只知道自己首次读取/观测到该消息的时间。由于改动前 occurred_at 必填，调用方将这个观测时间填入 occurred_at，并用此标记声明它不是原消息时间。服务不会自动生成这个标记；提取模型会看到 occurred_at=null，不能据此解释“本周”等相对日期，改动前 Worker 还会限制其更正/更新。

优化后把 received_at 与真实 occurred_at 分开，未知来源可以直接保留未知；adapter_observed 主要保留兼容已有这种请求。普通实时 Agent 不需要处理它，也不能仅因为正文描述过去就使用它。server_received 是本轮实现的实时缺省语义，由服务确定。

| 消息类型 | 提供真实 occurred_at | 省略 occurred_at |
| --- | --- | --- |
| 普通目标 messages | 按真实来源时间解析，日期新旧不影响首次保留期 | 默认实时接入，使用首次接收时间作为声明近似，记录 server_received 来源 |
| 导入适配程序显式标记时间未知的目标 messages | 如提供的只是观测时间，不视为真实来源日期 | 真实来源时间未知；仍可保存独立普通事实，不能用现在解析其相对日期 |
| history_messages | 按真实来源时间解析 | 来源日期未知；不默认为今天，仅按有依据的上下文辅助理解 |

沿用 source、adapter_observed 语义，增加服务端确定的 server_received 来源。普通调用无须填写来源类型；已知原消息时间由接入程序原样传递，历史导入缺时间时复用 metadata.timestamp_origin=adapter_observed 表示真实时间未知。此标记由掌握数据来源的适配程序填写，不要求业务 Agent 模型判断正文是过去还是现在。

“我2024年在北京住过”今天发来，是当前声明过去经历，不能根据正文的过去时把消息日期判为未知。反过来，旧档案里的“我现在住北京”也不能根据“现在”二字将来源日期判为今天。

系统无法单凭一条无来源日期、无未知标记的目标消息区分实时输入和旧档案；接口默认按实时处理。导入适配程序需要保留真实时间或明确未知，这个最小来源约定不可由模型猜测替代。

实现建议：来源新增 received_at；occurred_at 允许未知。显式 received_at 不由调用方控制。来源时间可空后，要审查 Worker、历史排序、治理和后台整理的全部时间读取，不能只修改 schema。

同一来源最初作为 history 被接收、之后作为目标提交时复用已记录接收时间；不能用再次提交刷新保留期。已知消息来源时间影响解释与迟到保护，首次接收时间影响新增记忆的可用与保留，两者各司其职。

### 3.2 首期支持的格式

- 保留 ISO8601 带时区格式。
- 支持 `2026-10-13 10:00:00` 和 `2026-10-13T10:00:00`，缺时区按北京时间。
- 保留目前已支持的空格加时区格式。
- 保留数字 Unix 秒/毫秒的既有能力，明确单位和标准化规则。
- 来源只有日期而无日内时间，不伪造精确声明顺序；自然语言日期优先放在正文解析。本轮不扩展任意自然语言 occurred_at 解析器。

“本周六”以消息时间在北京时间中的所在周确定；实时缺省使用首次接收日期。有可靠的历史来源日期则按历史周解析。缺少来源锚点、必要历史也无法确定是哪周时才报告时间不足。

### 3.3 幂等与时间规范化

先对显式时间格式做确定性规范化，再比较调用方请求内容；对省略时间的请求，不把每次生成的 now 混入请求指纹。命中原任务/原来源时复用首次补齐时间。

保存原始时间表达及规范化后的值用于追溯。发生时间未知与实时缺省必须参与来源语义区分，不能靠换幂等键将同一历史来源悄悄变成实时来源。

旧幂等键和来源 semantic_hash 按原协议版本验证，不能因为新增默认字段或统一展示时区就使旧请求重放冲突。新请求采用新规范化规则，时间语义/指纹版本可复用任务 config_version 区分；原有显式时间与新增接收时间分别保存。

真实来源时间与接收时间显著矛盾时给出明确诊断，不静默用接收时间覆盖显式来源。正常解析带 +09:00 的输入时应转换为北京时间，不能把它重新解释成 +08:00。本次动物园测试的时间倒序属于需要核实的数据问题，不能通过删除迟到保护修复。

## 4. 上下文与提取

### 4.1 保留现有消息窗口

保留最近 30 条普通历史和当前回复/回合/工具关联机制。history_messages 只辅助 targets，不独立提取旧陈述；已处理消息仍能作为上下文。

本轮不承诺跨窗口、跨会话、任意长度隐式指代均能恢复。未知指代报告 context_insufficient，不猜对象，也不能以 no_durable_value 掩盖缺依据。

### 4.2 将维护已有记忆纳入提取判断

提示词分别判断：

1. 新陈述是否值得形成记忆。
2. 新陈述是否在确认、细化、纠正、取消或限制已保存的信息。

第二类不要求新消息独立具有长期保存价值。不得将“确切说是周六”“还是不去了”“以后不按这个安排”统一当成单次执行进度。临时计划可以保存和维护，但不能推断计划已经实施。

候选事实须自足，引用至少一个目标用户消息及必要的历史原文。计划取消需保留对象、日期、原因；不能仅保存“用户要加班”而让旧计划继续有效，也不能推广成长期加班习惯。

### 4.3 为提取补充相关已保存状态

建议在提取之前提供有限的 related_memories：memory_id、正文、类型、状态和必要条件，使模型知道“这条计划已经保存”。本轮优先从当前会话来源关联的记忆中选择；其他同用户记忆作为跨会话上下文的使用属于后续扩展，须处理原文访问范围和证据契约。

候选记忆只辅助理解和定位，不独立产生新事实。需要其内容补足指代时，在现有授权/同会话范围内补入必要原文 history 并冻结来源版本；不能把候选 memory_id 冒充 message_id，也不能省略必要支持依据。

在输入预算中计入 related_memories 和补入原文，优先保留当前目标、必要原文，再保留有限状态候选和普通历史；避免新增状态上下文挤掉真正的证据。候选状态与版本进入冻结快照，提交时校验状态变化；变化时重做治理/选取，不使用失效的旧状态。

### 4.4 超预算边界

沿用切片和输入预算；超预算明确报告 CONTEXT_BUDGET_EXCEEDED，保留来源未完成。独立目标消息继续处理。

已有模型部分理解能力应保留：一个消息中有独立事实和缺上下文内容时，保存有依据部分，同时报告不足。因超大必要历史而整条消息无法进入模型的情况本轮保留限制，不强制新增复杂语义分句器。记录受影响目标/切片，不宣称已完成评估。

## 5. 治理和查询

- 保留明确更正/取消的 SUPERSEDE、补证据、争议和依赖失效流程；新事实替代后旧事实立即退出可用状态。
- historical 是内容属性，不再以此禁止纠正历史内容。对“去年住的是天津，不是北京”可以更正同一经历；不同年份的经历可以共存，不能仅按属性相同判冲突。
- 不再用新的记忆可用时间 effective_at 判消息新旧。迟到保护使用真实 occurred_at 或可信实时 server_received 声明时间；同会话相同时间用已记录的批次/位置解释明确前后关系。
- 接收较晚不意味着历史声明较新。历史导入不得凭新的 received_at 覆盖较新的当前状态。
- 时间未知仅在确实妨碍解释或裁决时阻止该项；取消 adapter_observed 对所有变更的一刀切过滤。对有充分指代和明确当前用户纠正的情况，按对应事实及依据裁决；真的无法裁决才 time_unresolved。
- 判重不比较系统补齐的生效/到期时间来要求完全相等，避免每次声明时间不同就形成重复。比较事实含义、事件/适用条件及用户明确保存要求；补证据不续期。
- 对补齐后的 effective_at、expired_at 统一校验合法性，不静默保存倒置区间。确定性的时间/输入拒绝不按模型网络故障盲重试，独立目标仍可处理。
- Add 可用结果和 Search 统一检查 active、effective_at <= now、未到期。有效的 historical 内容可以检索，但须保留“曾经/过去”条件，不能推断成当前状态。查询适用性模型显式接收北京时间的当前日期和时间，检查正文的活动截止、规则区间等条件，不能依赖模型猜现在的日期；系统保留期尚未到期不等于业务条件仍然满足。
- Profile 继续只纳入合适的长期当前信息，不把过去住址当成现住址。
- 同步审查 consolidation 等后台路径中对 historical 区间、effective_at 的旧假设；不能只修 Add 而由后台再次产生过期/混并问题。

## 6. outcome 与完成状态

| outcome | 优化后含义 | 来源是否完整 |
| --- | --- | --- |
| added / superseded / evidence_added / already_exists / disputed | 本次已提交动作，维持已有含义 | 无其他不足项时完整 |
| no_durable_value | 有足够上下文，确认既无新增价值，也不维护已有记忆 | 完整 |
| context_insufficient | 必要指代/原文缺失或必要上下文超预算 | 未完成 |
| time_unresolved | 时间缺失确实使日期解释或状态裁决无法完成 | 未完成 |
| evaluated_no_fact | 兼容路径或未分类空结果的诊断，不代表无价值 | 未完成 |
| already_processed | 当前来源版本已评估，幂等跳过；不保证产生或仍有可用记忆 | 保留原完成状态 |
| historical | 新任务停止用它表达已过期；旧任务响应按原记录保留 | 不重写旧记录 |

当前生产模型严格要求每个目标用户消息返回 assessment；缺失或自相矛盾按模型协议问题处理，不正常落成未分类成功结果。兼容提取器的兜底与生产协议问题分别统计。

新增稳定 reason_code，至少区分 MISSING_REFERENT、MISSING_DATE_ANCHOR、CONTEXT_BUDGET_EXCEEDED、UNKNOWN_STATEMENT_ORDER。自然语言 reason 继续用于说明，不作为调用方逻辑分支依据。

若需要在处理结果中公开内容类型和状态，按该项 memory_id 附加 temporal_kind 和提交时 memory_status，分别表达内容属性和状态快照；不能再挤进 outcome。results 继续仅列提交时可用记忆，event=ADD 保持兼容。

一个消息有保存和不足两类结果时，已保存内容不回滚，来源仍未完成；同一切片范围不能宣称是每个独立句子的精确范围。

## 7. 恢复与版本

普通 Add 保持同幂等键重放原任务；已完成来源保持跳过。补足合法上下文并用新幂等键提交未完成目标，可以重新评估，旧任务输入和结果不改写。

增加最小的受控重处理入口，建议先用管理命令：选定来源/任务、记录原因、创建新任务，走相同提取与治理流程。用于 no_durable_value 误判和规则升级；不是普通 Add 的无条件 force 开关。保留旧任务、证据和审计，既有已提交事实经判重处理。

来源时间修订必须单独记录版本和依赖处理，不通过直接更新表或删除来源绕过 MESSAGE_ID_CONFLICT。动物园原任务恢复须先核实显式来源时间，再按顺序重评估，不把已知倒序数据当成正确更新时间。

本轮不增加“任何新消息到来就重扫全部未完成来源”的自动机制。只在明确补充上下文或受控重处理时恢复，避免无限重复模型调用。

提取 prompt_version 和时间语义版本升级；新任务冻结 received_at、解析时区、所用原文、相关状态候选和预算。旧冻结输入不静默切换到新语义。

| 位置 | 必要改动 |

| api_schemas.py / API 接入 | occurred_at 可省略、北京时间规范化、按消息位置和已有未知时间标记处理，服务确定时间来源 |
| models.py / migrations | 保存来源首次 received_at，支持真实来源时间未知；原字段和审计保留 |
| ingest.py | 首次补时间、时间规范化、原任务/来源重放，避免动态时间改变指纹 |
| providers.py | 提取维护临时状态、historical 内容语义、事件日期正文、完整 assessments；扩展有限状态上下文 |
| extraction_input.py / worker.py | 状态上下文与必要原文预算、冻结、canonical 生效时间、合法区间、治理时间判断、结果动作 |
| ttl.py | 确认生效时间已按新语义规范化；明确保存期限优先，移除事件/历史区间默认过期含义 |
| task_results.py / 响应 schema | reason_code，新任务停止产生旧 historical outcome；保留旧响应兼容 |
| retrieval.py / profile.py / consolidation.py | 一致可用条件、历史内容条件、后台旧时间假设与判重 |
| 管理命令 | 有审计的选定来源重处理及必要的来源修订流程 |
| docs / tests / 模型评估 | 更新契约、迁移说明、端到端回归和真实模型案例 |

旧来源 received_at 可从来源首次 created_at 迁移为已知的落库近似，记录其推定性质；不声称恢复了当年的 HTTP 接收时间。存量 adapter_observed 原始值保留审计，读取时区分未知原时间与观测时间。

不批量将旧 expired 改 active，不重写旧 outcome 或来源时间，不静默改已有 TTL。先导出受影响范围，再通过选定重处理建立新语义记录，防止恢复已取消或已被更正的事实。

## 9. 实施顺序

1. 时间接入与数据契约 → 验证：实时缺省、历史未知、北京时间、重试幂等、received_at 固定。
2. 提取与时间规范化 → 验证：过去经历正常保存、事件日期自足、计划立即可用、默认保留期不从过去起算。
3. 上下文和治理 → 验证：细化/取消能替代、来源新旧保护不误用 effective_at、必要依据不被状态候选挤掉。
4. outcome、恢复与读取/后台一致性 → 验证：动作与状态分开、不足不标完成、历史事实可检索、管理重处理保留审计。
5. 相关回归和真实模型评估 → 验证：以下场景通过后，再评估上线迁移；本文件不执行部署或数据库改写。

## 10. 验收场景

| 场景 | 期望结果 |
| --- | --- |
| 三次实时 Add：周末去动物园 → 确切说周六 → 不去，要加班 | 第一次 temporary added；第二次日期细化并 superseded；第三次取消并 superseded；旧计划不可用，保留对象、日期、原因 |
| 2026-10-13 实时输入“这周六去动物园”，省略时间 | 北京时间解析为 2026-10-17；正文明确日期；首次接收起可用 |
| 历史消息有来源日期，说“这周六” | 按原来源所在周解析，而非导入所在周 |
| 历史消息无来源日期，说“这周六”且无其他可靠锚点 | 仅时间相关陈述报告不足，不猜具体日期 |
| 一批目标混合当前消息和有真实日期的旧消息 | 分别使用各自时间锚点，无请求级模式冲突；新增保留期按首次接收计算 |
| 今天说过去经历，或旧档案中出现“现在” | 正文时态只决定内容属性，不冒充消息来源日期 |
| “我以前在北京住过”，没有起止日期 | historical、regular、active、added；从首次接收起默认 180 天；可查询过去居住经历 |
| 今天首次导入 2024 年的居住经历或旧普通事实 | 不因过去日期刚导入就 expired；保留原时间含义 |
| 今天说“自2020年至今客户联系人一直是李明” | 当前事实正常可用，TTL 不从 2020 年耗尽 |
| 未来事件计划 | 事件日期保留正文，记忆现在可用；提前取消不因未来事件日拒绝 |
| 明确未来生效规则 | 生效不早于 received_at，规则开始前不可作为已生效规则使用 |
| 过去事件结束/规则适用截止 | 日期为正文条件，不等于系统立即忘记；查询不得扩大适用范围 |
| 同键重试、换键重投相同来源、Worker 重试 | received_at 和缺省时间不变；无指纹冲突或 TTL 刷新 |
| 重复事实、同一支持组再提交 | 判重/补证据正确，不重复新增，不续期 |
| 迟到历史与当前状态冲突 | 不因新 received_at 覆盖较新当前状态 |
| 纠正同一过去经历，不同年份独立经历 | 前者允许明确替代，后者保守共存 |
| 上下文超预算 | 明确不足、来源未完成、独立目标继续；不误报无价值 |
| 模型漏 assessment 或同消息事实与无价值矛盾 | 明确协议失败，不误标完整 |
| 区间补齐后倒置、确定性时间拒绝 | 不写非法区间，不盲重试；明确诊断 |
| 受控重处理已完成误判来源 | 新任务留审计、旧任务保留，既有事实不重复 |
| 新旧 prompt、时间契约及迁移 | 冻结输入不混用版本，旧响应可读，存量不会自动复活 |

确定性回归验证状态、时间公式、证据和幂等；真实模型评估单独验证分类、日期解析、指代、计划细化和取消。不能用 FakeFactModel 通过代替真实模型质量验收。
