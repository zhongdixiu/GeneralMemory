# 审计模块运行说明

## 查询入口

使用 `GET /api/v1/audit-logs`。在现有业务 Agent 凭证上开启 can_read_audit_content=true 即可读取审计正文，无需独立管理 token 或治理权限。仅开启 can_manage_governance=true 也可查询审计元信息；查询范围固定为该凭据的租户，客户端不能指定其他租户。

```text
# 最近的业务事件
GET /api/v1/audit-logs

# 一条记忆的时间线
GET /api/v1/audit-logs?target_type=memory&target_id=mem_example

# 一次处理链路；包括归并画像任务和关联的撤销事件
GET /api/v1/audit-logs?correlation_id=example_chain

# 一个任务产生的事件
GET /api/v1/audit-logs?task_id=tsk_example

# 展开向量维护、任务入队等技术事件
GET /api/v1/audit-logs?include_technical=true

# 查看完整历史快照和关联信息，需要内容权限
GET /api/v1/audit-logs?target_type=memory&target_id=mem_example&include_details=true
```

支持 `target_type`、`target_id`、`correlation_id`、`task_id`、`reason_code` 筛选；`target_id` 必须同时提供 `target_type`。分页使用 `limit`（默认 50，最多 100）、`offset`；返回 `has_more` 表示是否还有下一页。

默认列表按时间和流水 ID 倒序，对象、链路和任务时间线按时间和流水 ID 正序；相同时间戳的顺序稳定。展开技术明细后，记忆时间线也包含该记忆的向量事件，模型身份需结合快照/关联中的 `model_id` 阅读。

每个事件包含中文 `event_name`、目标、动作、操作者、原因、关联 ID 和 `changes`。默认变化只展示状态、版本、时间、置信度、争议组和证据数量；允许内容读取时另显示最多 160 字的 `summary`。完整 JSON 只在请求 `include_details=true` 时返回。

## 内容权限

`can_manage_governance` 允许查看事件元信息，不自动授予用户内容读取权限。can_read_audit_content=true 可独立允许审计查询及正文详情，不同时开放治理、修改或删除接口。原因中的自由文本、对象正文、画像值和嵌套证据都可能包含用户原文，需要显式开启此内容开关。

给确实允许查看整个租户审计内容的凭据显式增加此字段，例如：

```json
{
  "token": "replace-with-a-long-random-token",
  "tenant_id": "tenant_example",
  "caller_agent_id": "email_agent",
  "allowed_source_systems": ["email_agent"],
  "can_read_audit_content": true
}
```

更新 `MEMORY_AUTH_CREDENTIALS_JSON` 后重启 API。此权限目前是租户级权限，不提供用户级内容授权。

无内容权限时 `reason` 和 `summary` 为 null，完整状态及 context 不返回；强行请求 `include_details=true` 返回 403。中文事件名称仍可读。已有治理运行操作接口 `/api/v1/governance/runs/{run_id}/operations` 的 `details` 也受同一内容权限控制，未授权时为 null；操作 ID、kind、memory_id 和撤销状态仍可见。

## 写入契约

- 所有运行期审计调用统一使用 `record_audit`，与对应业务变更处于同一事务。INSERT 无前态、DELETE 无后态使用 SQL NULL；历史 JSON null 继续兼容。
- `reason_code` 表达事件，`reason` 保存具体决策原因；没有具体决策原因时记录固定事件说明。reason 最长 512 字，治理操作中的完整说明仍保留在 `governance_operation.details`。
- `target_type/target_id` 指实际变更对象。推断创建为 memory INSERT，争议为 memory UPDATE，策略变更为 governance_policy UPDATE。
- `operator_type/operator_id` 表达该变更的执行者；接入调用者为 agent，Worker 为 system，人工撤销为 admin。任务的调用者另存 `context.initiator_id`。
- `state_before/state_after` 是本事件涉及字段的前后值，不能用于完整重建对象。证据组、消息、画像依据和治理操作 ID 放在 `context`，复杂治理快照仍保存在 operation.details。
- 新事实的初始证据归入创建日志。重复陈述追加证据单独记录，展示证据数量变化。合并的被停用记忆和保留记忆分别记录状态及证据变化；撤销时分别记录恢复变化。
- 未通过时间/范围校验的抽取候选保留在任务 diagnostics，不再制造来源 UPDATE；疑似过时但未改变记忆的判断保留在治理操作表。
- 每次接入生成独立 `correlation_id`；客户端 `X-Request-ID` 保存在任务 payload 中用于请求定位。重复请求重放返回原任务，不新增审计。
- Worker 日志带 `task_id`。画像任务归并时将全部触发链路写入 payload/context 的 `trigger_correlation_ids`；没有链路 ID 的旧后台任务在执行时生成新 ID。
- 撤销生成新的关联 ID，同时保留 `context.operation_id`、`original_correlation_id` 和原任务身份，不再将任务 ID 当作链路 ID。

## 历史数据兼容

迁移 `0006_audit_events` 只增加可空的 task_id/context、查询索引和 governance_policy 目标约束，不改写或删除历史日志。

读取层兼容历史 task 目标的推断/治理操作，通过同租户 `operation_id` 关联真实记忆；也兼容旧策略目标、争议 INVALIDATE 动作和撤销使用任务 ID 作为 correlation 的记录。详情仍返回原始快照，便于对照。

兼容读取不能恢复历史缺失的信息：没有 operation 关联的旧日志无法推断真实目标；没有任务身份的旧日志按 task_id 筛选不保证完整；旧创建顺序、缺失原因和错误失效理由保留原记录，不凭空补写。

## 只追加保护与数据库权限

ORM 拒绝对已写入的 MemoryAuditLog 执行修改和删除。直接 SQL、Core 批量操作和表所有者仍能绕过 ORM，因此部署必须使用与迁移/维护账号分开的业务角色。

下面是为**已有、非表所有者**业务角色 `memory_runtime` 设置审计权限的示例。先确保该角色不是超级用户，也不继承表所有者或其他具有写改权限的角色；其他业务表权限仍按原部署配置维护。

```sql
REVOKE UPDATE, DELETE, TRUNCATE ON public.memory_audit_log FROM PUBLIC;
REVOKE UPDATE, DELETE, TRUNCATE ON public.memory_audit_log FROM memory_runtime;
GRANT SELECT, INSERT ON public.memory_audit_log TO memory_runtime;
GRANT USAGE ON SEQUENCE public.memory_audit_log_id_seq TO memory_runtime;
```

迁移和测试清理继续使用维护角色。本次迁移不创建数据库登录账号，不改现有凭据或角色权限；如果 API/Worker 继续使用表所有者，数据库层“只追加”仍不能保证。

## 验证

数据库升级后运行审计及相关测试，并检查模型漂移：

```sh
poetry run alembic upgrade head
poetry run pytest -q tests/test_audit.py tests/test_add_worker.py tests/test_fact_governance.py tests/test_consolidation.py tests/test_profile.py tests/test_governance_worker.py
poetry run alembic check
poetry run ruff check src tests migrations/versions/0006_audit_events.py
```

测试不需要真实模型调用。若当前环境设置了 SOCKS 代理而没有 socksio，运行这些测试前清除测试进程的 HTTP_PROXY/HTTPS_PROXY/ALL_PROXY 及其小写变量；不修改应用的生产网络配置。

全量迁移测试应使用独立的空测试数据库；旧画像迁移测试会恢复 property_key NOT NULL，不能在已包含独立画像陈述的业务库上验证该前置条件。

当前全库 `alembic check` 存在既有的向量模型漂移：0002 保留了 embedding_legacy，并允许新的 embedding 为空，ORM 未表达这两项。该问题独立于审计迁移，本次未修改；审计表的模型一致性由 test_audit_schema_matches_metadata 单独检查。
