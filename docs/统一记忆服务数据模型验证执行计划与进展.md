## 2. 进展维护规则

每次完成一个可独立验证的工作批次后，必须同步更新本文档：

1. 更新“当前进展总览”中的状态和完成日期；
2. 在对应阶段记录实际交付物、执行命令和验证结果；
3. 记录实现与冻结设计的偏差、未决问题及阻塞；
4. 明确下一阶段及其开始条件；
5. 只有代码或 migration 已实际执行且验收项通过，才能标记为“已完成”；
6. 部分完成时保持“执行中”，不得用计划内容代替实际结果；
7. 发生 No-Go 条件时停止扩大实现范围，先记录问题和最小修订建议。

状态定义：

| 状态 | 含义 |
| --- | --- |
| 未开始 | 尚未进入实施 |
| 执行中 | 已开始，但阶段验收未全部通过 |

| 阻塞 | 因外部依赖、权限或输入缺失无法继续 |

## 7. 第三批：证据组与生命周期

状态：已完成
完成日期：2026-09-21

### 7.1 实施范围

- OR：多个独立证据组；
- AND：同一证据组包含多个共同依据；
- 多事实共同支撑推断；
- 记忆到画像的 `profile_basis`；
- 来源失效、记忆失效、TTL、纠正、替代和争议；
- 下游递归检查、画像重建及向量删除任务创建。

### 7.2 验收标准

- 完整性判断遍历 evidence group 的全部历史组成边；
- 完整边必须同时满足边有效、上游有效、版本一致且未过期；
- 任一完整组存在时下游可以继续有效；
- 所有组均不完整时下游立即停止在线使用；
- TTL 到期任务未执行时，在线检索仍能立即排除；
- 完成冻结用例 T01～T07、T09、T15、T16。

### 7.3 No-Go 条件

- AND/OR 充分性语义无法稳定实现；
- 来源失效后仍能通过正常检索获得依赖记忆；
- 依赖传播必须结构性修改冻结模型才能实现。

### 7.4 实际交付与验证结果

- evidence group 完整性判断遍历全部历史边，并逐项校验边状态、上游状态、版本和 TTL；
- 来源更新或失效时保留并失效旧 supports 边，随后同步重检全部下游；
- 所有证据组均不完整时，记忆或画像立即失效，并递归处理 derives/profile_basis 下游；
- 记忆失效或 TTL 到期时，按现有向量模型生成幂等 `vector_delete` 任务；
- TTL 到期任务未执行时，在线检索仍依据 `expired_at` 排除；执行到期转换时同步写审计、
  向量删除任务和下游重检；
- 验证明确纠正与替代关系，以及 disputed 记忆不进入在线检索；
- 建立显式编号测试并完成 T01～T07、T09、T15、T16。

## 8. 第四批：PostgreSQL 异步任务队列

状态：已完成
完成日期：2026-09-21

### 8.1 实施范围

- 任务幂等入队；
- `priority`、`available_at` 调度；
- `FOR UPDATE SKIP LOCKED` 并发领取；
- `worker_id`、`locked_until` 租约和续租；
- 失败重试、退避、过期租约接管；
- 任务完成时的 Worker 所有权检查；
- `input_version` 防止旧结果覆盖新版本；
- `correlation_id` 在任务和审计链路中传播。

### 8.2 验收标准

- 两个独立数据库连接不会领取同一任务；
- 未过期租约不能被其他 Worker 接管；
- 租约过期后可以安全接管；
- 原 Worker 失去租约后不能完成任务；
- 优先级领取顺序为 100、50、0；
- 未来 `available_at` 任务不能提前领取；
- 旧版本任务更新影响 0 行；
- 完成冻结用例 T10、T12、T17～T19。

### 8.3 实际交付与验证结果

- 实现任务幂等入队、`FOR UPDATE SKIP LOCKED` 原子领取和三级优先级调度；
- 支持 `available_at` 延迟执行、租约续期、过期租约接管及 Worker 所有权检查；
- 支持失败退避、重试计数、达到上限转为 failed，并在重试时清空 Worker 和租约；
- 任务完成、续租、失败均要求 processing 状态、当前 Worker 且租约未过期；
- 使用 `input_version` 条件更新业务对象，旧任务影响 0 行并转为 cancelled；
- 使用两个真实独立数据库连接验证 `SKIP LOCKED` 不会重复领取；
- 验证任务和审计沿完整链路继承相同 `correlation_id`；
- 完成冻结用例 T10、T12、T17、T18、T19。

## 9. 第五批：范围、向量检索与性能冒烟

状态：已完成
完成日期：2026-09-21

### 9.1 数据量级决策

本阶段验证目标是发现范围隔离、向量一致性、索引可用性和明显查询退化，不承担生产容量证明，
也没有生产 SLA。因此将原“至少一万条”调整为分层执行：

- 默认量级：3000条记忆、3000条来源、3000条证据边及对应向量；
- 升级量级：仅当默认量级下查询计划无法稳定判断 HNSW 或范围索引行为时，升至1万条复核；
- 小型生命周期 fixture 继续负责精确行为断言，不与批量性能数据混用。

3000条1536维 `float32` 向量的原始向量载荷约17.6 MiB；每个1%边界桶仍有约30条数据，
足以覆盖低频状态，同时相对1万条减少约70%的生成和重建工作。1万条不再作为 MVP 固定验收门槛。

### 9.2 已完成的数据准备

- 新增 `memory_cmic.smoke_data`，使用专用租户 `tenant_wp5_smoke` 可重复重建虚构数据；
- 覆盖 user、agent、company 三路主体及通用、单值、多值业务/项目范围；
- 覆盖 invalidated、disputed、expired、active 但 TTL 已到期和未来到期；
- 覆盖 active/stale 向量、`content_hash` 不一致和第二个 `model_id`；
- 每条记忆附带一条来源和 supports 证据边，用于来源反向依赖查询；
- 已实际装载3000条记忆、3000条来源、3000条证据边和3030条向量，耗时14.581秒；
- 当前 `memory_embedding` 表（含索引）占49 MiB，HNSW 索引占24 MiB；
- 预检查 `EXPLAIN` 已选择 `ix_memory_embedding_active_hnsw`，无须升级至1万条；
- 造数定向测试：2 passed；造数阶段全量测试：59 passed。

准备命令：

```text
poetry run python -m memory_cmic.smoke_data --count 3000
```

命令只替换专用租户下由该生成器维护的四类数据，不改动生命周期 fixture 或其他租户。

### 9.3 检索实现与行为结果

- 用户、Agent 和 company 三路主体分别应用租户、状态、TTL、业务域和项目域过滤，再合并排序；
- 向量检索必须显式传入 `model_id`，使用 cosine distance；
- 仅返回 active 向量，并在 SQL 中校验向量 `content_hash` 与当前 `summary + "\n" + content` 一致；
- T08 六组范围期望、多主体合并、cosine 精确匹配、stale 状态/哈希排除和双模型选择均通过；
- 定向验证 `22 passed`；全量验证 `62 passed`。

### 9.4 轻量性能冒烟

在3000条记忆、3030条向量上每类查询执行30次：

| 查询 | p50 | p95 |
| --- | ---: | ---: |
| 单租户、单主体向量查询 | 12.521 ms | 18.093 ms |
| 业务域、项目域过滤向量查询 | 9.741 ms | 10.502 ms |
| 三路主体向量召回 | 23.987 ms | 30.199 ms |
| TTL 扫描 | 0.942 ms | 1.455 ms |
| 来源反向依赖查询 | 0.753 ms | 1.412 ms |

查询计划结果：

- HNSW 预检查选择 `ix_memory_embedding_active_hnsw`；
- TTL 扫描选择 `ix_memory_item_active_expired_at`；
- 来源反查选择 `ix_evidence_upstream_source`；
- 完整范围过滤向量查询在当前量级下由优化器选择顺序扫描3030条向量，向量表扫描
  约0.7 ms，完整 `EXPLAIN ANALYZE` 约9.1 ms，未观察到明显退化；
- 不强制 planner 使用 HNSW，也不在 MVP 阶段新增推测性索引。数据量或过滤后选择性提高时，
  最小复核项是 pgvector iterative scan，再评估分区或分域向量索引。

可复现命令：

```text
poetry run python -m memory_cmic.retrieval_smoke \
  --iterations 30 --output reports/wp5_performance_smoke.json
```

完整 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 保存在
`reports/wp5_performance_smoke.json`。默认量级已能判断 HNSW 可用性、范围索引行为和实际优化器选择，
因此未升至1万条。

### 10.5 实际数据结论与设计偏差

- 因此冻结文档中的统一 `source_ids -> supports` 假设不适用于当前源库。经确认后采用
  `internal_metadata.message_ids -> supports`、`source_ids -> derives`；
