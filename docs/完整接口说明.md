# MemoryCMIC 完整接口说明

本文依据当前 `src/memory_cmic/api.py`、`api_schemas.py`、`profile_config.py` 和响应构造代码整理，覆盖全部 **19 个业务路由**。示例中的 ID、token 和时间仅用于说明；返回的实际 ID、时间、模型结果及治理结果由运行时决定。

## 阅读约定

- 基础地址示例：`http://localhost:8000`。以下命令使用 `API`、`TOKEN` 环境变量，可先在本地终端设置：

  ```bash
  export API='http://localhost:8000'
  export TOKEN='替换为已配置的服务凭证'
  ```

  所有业务路由都要求 `Authorization: Bearer <token>`；租户由 token 绑定，不能在请求中指定。
- 发送 JSON 正文时使用 `Content-Type: application/json`。可选 `X-Request-ID` 最长 128 字符；未传或过长时服务生成新值，并在响应头回传。POST/PUT 正文超过 2 MiB 返回 `413 PAYLOAD_TOO_LARGE`。
- JSON 请求模型拒绝未定义字段。大部分请求模型要求省略不用的可选字段，不接受显式 `null`；画像维度配置的新增 `key` 可省略或传 `null`，示例采用省略写法。Query/Path 参数按各接口说明校验。时间响应使用带时区的 ISO 8601 字符串；示例中的时间只是示意。
- 通用错误格式：`{"error":{"code":"错误码","message":"说明"}}`。无效 Bearer 凭证返回 `401 UNAUTHENTICATED`；权限不足返回 `403 FORBIDDEN`；无效 JSON 返回 `400 INVALID_JSON`；请求字段不合法通常返回 `422 INVALID_MESSAGE`。各接口的特有错误另行说明。
- `user_id` 当前由受信任后端提供，本服务没有核验终端登录用户与该 ID 的绑定。凭证中的 `allowed_source_systems` 限制 Add 写入来源；`can_manage_memories`、`can_manage_governance`、`can_read_audit_content` 分别控制管理、治理和审计内容能力。

## 1. 提交对话：`POST /api/v1/memories:add`

**功能与权限：** 持久化消息来源并创建 `fact_extract` 任务。凭证必须允许写入请求的 `source_system`。此接口成功表示接入或处理完成，具体取决于返回状态。

**Header**

| 字段 | 必填 | 含义与取值 |
| --- | --- | --- |
| `Authorization` | 是 | `Bearer <token>`；租户及可信调用 Agent 来自凭证 |
| `Idempotency-Key` | 是 | 1～128 个 ASCII 字符；同一调用范围内同键同请求返回原任务，同键不同请求返回 409 |
| `Content-Type` | 是 | `application/json` |
| `X-Request-ID` | 否 | 调用方链路 ID，最长 128 字符；回传于响应头 |

**JSON 输入**

| 字段 | 必填 | 含义与取值 |
| --- | --- | --- |
| `source_system` | 是 | 来源系统，1～64 字符；必须在凭证允许写入的来源列表中 |
| `user_id` | 是 | 本次消息所属用户，1～128 字符 |
| `session_id` | 是 | 来源会话 ID，1～128 字符 |
| `messages` | 是 | 本次待处理消息，1～100 条，元素结构见下表 |
| `history_messages` | 否 | 上下文消息，0～100 条；用于理解目标消息，不单独形成新事实；默认 `[]` |
| `agent_id` | 否 | 标记来源 Agent，1～128 字符、非全空白；默认凭证的 `caller_agent_id`，不改变权限 |
| `wait_for_result` | 否 | 布尔值，默认 `false`；`true` 时短暂等待任务结束 |
| `wait_timeout_ms` | 否 | 等待上限 1～30000 毫秒；仅在 `wait_for_result=true` 时可传，省略时等 10000 毫秒 |

`messages`、`history_messages` 中每条消息的字段：

| 字段 | 必填 | 含义与取值 |
| --- | --- | --- |
| `message_id` | 是 | 来源消息 ID，1～256 字符；同一请求内不能重复 |
| `role` | 是 | `user`、`assistant`、`tool`、`system` |
| `content` | 是 | 消息文本，最多 64 KiB UTF-8；无非空文本时需有工具调用或附件引用 |
| `occurred_at` | 否 | 消息发生时间；建议传带时区 ISO 8601，例如 `2026-10-16T09:00:00+08:00`。仅日期字符串不合法；无时区的日期时间按 `Asia/Shanghai` 解释 |
| `author_id` | 否 | 作者 ID，1～128 字符。`user` 消息只能省略或等于 `user_id`；`assistant` 消息只能省略或等于来源 `agent_id` |
| `turn_id` | 否 | 对话轮次 ID，1～128 字符 |
| `reply_to_message_id` | 否 | 所回复消息的 ID，1～256 字符 |
| `metadata` | 否 | 消息元数据；默认使用空元数据，子字段见下表 |

`metadata` 字段：

| 字段 | 必填 | 含义与取值 |
| --- | --- | --- |
| `channel` | 否 | 渠道，1～64 字符 |
| `timestamp_origin` | 否 | `source`（默认，来源时间）或 `adapter_observed`（接入适配器观察时间） |
| `tool_name`、`tool_call_id` | 工具消息必填 | 工具名称与调用 ID，各 1～128 字符；非 `tool` 消息不能提供工具结果元数据 |
| `tool_status` | 工具消息可省略 | `succeeded`、`failed`、`unknown`；工具消息省略时补为 `unknown` |
| `tool_calls` | 否 | 最多 20 项，仅 `assistant` 消息允许；每项必含 `tool_call_id`（1～128）、`tool_name`（1～128），可含 `arguments`（JSON 对象，默认 `{}`，最多 8 KiB） |
| `attachments` | 否 | 最多 20 项；每项含 `file_id`（1～256）、`mime_type`（1～128），可含 `name`（1～256）和 64 位小写十六进制 `sha256` |
| `extensions` | 否 | JSON 对象，最多 8 KiB；整个 `metadata` 最多 16 KiB |

`history_messages` 中明确的来源时间不能晚于本次目标消息的明确来源时间。同一消息 ID 绑定不同语义内容会返回 `409 MESSAGE_ID_CONFLICT`，重复使用已失效来源会被拒绝。

**响应：** 任务仍在等待/处理时 HTTP `202`，终态时 HTTP `200`。`status` 为 `pending`、`succeeded`、`partial`、`failed` 或 `cancelled`；数据库内的 `processing` 对外显示为 `pending`。

| 响应字段 | 含义 |
| --- | --- |
| `task_id` | 抽取任务 ID，用于后续查询 |
| `status` | 对外任务状态；`partial` 表示已有部分变更提交，后续处理失败 |
| `results` | `pending` 时为 `null`；终态为可用的新记忆数组，元素含 `id`、`memory`、`event`（固定 `ADD`）；可能为空数组 |
| `processing_results` | `pending` 时为 `null`；终态时可为数组或 `null`。每项含 `message_id`、可选原文片段 `start_char`/`end_char`、`outcome`、`memory_ids`、`reason`、`reason_code`、`temporal_kind`、`memory_status` |
| `error` | 无错误时 `null`；失败/部分完成时含 `code`、`message` |

`processing_results[].outcome` 可为 `added`、`evidence_added`、`already_exists`、`superseded`、`disputed`、`historical`、`no_durable_value`、`context_insufficient`、`evaluated_no_fact`、`already_processed`、`time_unresolved`。`results=[]` 也可能表示重复事实只补了证据，应结合处理结果判断。

**调用示例**

```bash
curl -X POST "$API/api/v1/memories:add" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: add-user-1001-001' \
  -d '{"source_system":"email_agent","user_id":"user_1001","session_id":"session_101","messages":[{"message_id":"msg_101","role":"user","content":"以后周报请先写结论。","occurred_at":"2026-10-16T09:00:00+08:00"}]}'
```

```json
{"task_id":"tsk_example","status":"pending","results":null,"processing_results":null,"error":null}
```

常见特有错误：`403 FORBIDDEN`（来源系统无写权限）、`409 IDEMPOTENCY_CONFLICT`、`409 MESSAGE_ID_CONFLICT`、`422 INVALID_MESSAGE`。

## 2. 查询 Add 任务：`GET /api/v1/tasks/{task_id}`

**功能与权限：** 查询原调用 Agent 提交的任务。仅同租户且同 `caller_agent_id` 可见；请求不需要也不接受来源 `agent_id`。

**Header：** `Authorization: Bearer <token>` 必填；`X-Request-ID` 可选。**Path 参数：** `task_id` 必填，1～128 字符，Add 返回的任务 ID。**Query/Body：** 无。

**响应：** HTTP `200`，字段与第 1 节的 `TaskResponse` 完全相同。内部 `processing` 仍显示为 `pending`；任务未找到或不属于该调用身份返回 `404 TASK_NOT_FOUND`。

```bash
curl "$API/api/v1/tasks/tsk_example" -H "Authorization: Bearer $TOKEN"
```

```json
{"task_id":"tsk_example","status":"succeeded","results":[{"id":"mem_example","memory":"用户要求周报先写结论。","event":"ADD"}],"processing_results":[{"message_id":"msg_101","start_char":0,"end_char":10,"outcome":"added","memory_ids":["mem_example"],"reason":null,"reason_code":null,"temporal_kind":"current","memory_status":"active"}],"error":null}
```

## 3. 检索记忆：`POST /api/v1/memories:search`

**功能与权限：** 从指定用户的当前有效事实和推断中检索。凭证需具有非空 `allowed_source_systems`。此接口只返回记忆，不返回模型理由、画像或原始对话。

**Header：** `Authorization: Bearer <token>`、`Content-Type: application/json` 必填；`X-Request-ID` 可选。

| JSON 字段 | 必填 | 含义与取值 |
| --- | --- | --- |
| `user_id` | 是 | 目标用户，1～128 字符 |
| `query` | 是 | 任务描述，1～8000 字符且不能全为空白 |
| `limit` | 否 | 最多返回条数，1～50，默认 10；实际可少于上限 |
| `use_model` | 否 | 严格 JSON 布尔值，默认 `false`。`true` 时增加模型适用性判断；两种模式都需要 embedding 服务 |
| `agent_id` | 否 | 来源 Agent 过滤，1～128 字符、非全空白；不是本次调用 Agent |
| `source_system` | 否 | 原始来源系统过滤，1～64 字符、非全空白；与 `agent_id` 同时给出时共同生效 |

**响应：** HTTP `200`，`results` 为数组；每项 `id` 是记忆 ID，`memory` 是完整陈述，`cognitive_type` 为 `fact` 或 `inference`。无结果返回 `[]`。请求依赖的 embedding 服务未配置返回 `503 SEARCH_UNAVAILABLE`；模型或 embedding 调用失败返回 `502 SEARCH_FAILED`。

```bash
curl -X POST "$API/api/v1/memories:search" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"user_id":"user_1001","query":"写项目周报","limit":10,"use_model":true}'
```

```json
{"results":[{"id":"mem_example","memory":"用户要求周报先写结论。","cognitive_type":"fact"}]}
```

## 4. 读取画像：`GET /api/v1/profiles`

**功能与权限：** 读取已经由 Profile Worker 生成的用户画像，不在请求中调用重建模型。凭证需具有非空 `allowed_source_systems`。

**Header：** `Authorization: Bearer <token>` 必填；`X-Request-ID` 可选。**Body：** 无。

| Query 字段 | 必填 | 含义与取值 |
| --- | --- | --- |
| `user_id` | 是 | 目标用户 ID，1～128 字符 |
| `include_inferred` | 否 | 布尔值，默认 `false`；`true` 时纳入已允许生成且仍有效的推断画像 |

**响应：** HTTP `200`。

| 响应字段 | 含义 |
| --- | --- |
| `profiles` | 画像陈述数组；同一个 `property_key` 可以出现多条 |
| `profiles[].id` | 画像记录 ID |
| `profiles[].assertion_kind` | `explicit`（明确依据）或 `inferred`（推断依据） |
| `profiles[].property_key` | 租户画像维度的稳定 key |
| `profiles[].property_value` | 完整画像陈述 |
| `profiles[].value_type` | 当前固定为 `string` |
| `profiles[].business_domains` | 适用业务场景数组；`null` 表示未按此维度限定 |
| `config_version` | 租户当前画像配置版本 |
| `applied_config_version` | 当前用户画像已应用的配置版本，可为 `null` |
| `status` | `ready`、`pending` 或 `failed`；配置尚未应用时旧画像不输出 |

```bash
curl "$API/api/v1/profiles?user_id=user_1001" -H "Authorization: Bearer $TOKEN"
```

```json
{"profiles":[{"id":"prf_example","assertion_kind":"explicit","property_key":"communication","property_value":"用户希望周报先写结论。","value_type":"string","business_domains":null}],"config_version":1,"applied_config_version":1,"status":"ready"}
```

## 5. 读取租户画像维度：`GET /api/v1/profile-config`

**功能与权限：** 读取本租户的完整画像维度配置；首次读取会初始化默认配置。任何有效服务凭证均可调用。

**Header：** `Authorization: Bearer <token>` 必填；`X-Request-ID` 可选。**输入：** 无 Path、Query 或 Body 参数。

**响应：** HTTP `200`。`version` 为正整数配置版本；`dimensions` 为有序数组，每项的 `key` 是稳定维度标识，`name` 是显示名称，`description` 是分类说明，`enabled` 是是否启用。默认维度完整列表见 [租户画像维度配置运行说明](租户画像维度配置运行说明.md#数据与默认配置)。

```bash
curl "$API/api/v1/profile-config" -H "Authorization: Bearer $TOKEN"
```

```json
{"version":1,"dimensions":[{"key":"identity","name":"基本身份","description":"用户本人的长期身份信息。","enabled":true}]}
```

上例只展示一个数组元素以说明结构，实际默认配置含多项维度；`description` 的实际内容以接口返回为准。

## 6. 更新租户画像维度：`PUT /api/v1/profile-config`

**功能与权限：** 整体替换本租户的维度配置，需 `can_manage_governance=true`。省略的旧维度会被移除；同一配置重复提交不增加版本。

**Header：** `Authorization: Bearer <token>`、`Content-Type: application/json` 必填；`X-Request-ID` 可选。

| JSON 字段 | 必填 | 含义与取值 |
| --- | --- | --- |
| `expected_version` | 是 | 当前配置版本，严格正整数；用于避免覆盖其他人的修改 |
| `dimensions` | 是 | 完整有序维度数组，0～32 项；可传空数组以关闭所有维度 |
| `dimensions[].key` | 更新旧维度时是 | 已存在维度的稳定 key，格式为小写字母/数字/下划线、1～128 字符；新增维度必须省略，由服务生成 `dim_...` |
| `dimensions[].name` | 是 | 显示名称，1～128 字符且不能全为空白；同一次提交不能重名 |
| `dimensions[].description` | 是 | 分类说明，1～2048 字符且不能全为空白；启用维度的总输入还受模型预算限制 |
| `dimensions[].enabled` | 否 | 严格 JSON 布尔值，默认 `true` |

**响应：** HTTP `200`，结构同第 5 节，返回保存后的 `version` 和完整 `dimensions`。版本不符返回 `409 PROFILE_CONFIG_CONFLICT`；未知旧 key、重复名称/key 或预算超限返回 `422 INVALID_PROFILE_CONFIG`（字段基础校验失败时为 `422 INVALID_MESSAGE`）。

```bash
curl -X PUT "$API/api/v1/profile-config" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"expected_version":1,"dimensions":[{"key":"identity","name":"基本身份","description":"仅收录用户明确且长期有效的身份信息。","enabled":true},{"name":"宠物背景","description":"用户明确饲养的宠物及其长期习惯。","enabled":true}]}'
```

```json
{"version":2,"dimensions":[{"key":"identity","name":"基本身份","description":"仅收录用户明确且长期有效的身份信息。","enabled":true},{"key":"dim_generated","name":"宠物背景","description":"用户明确饲养的宠物及其长期习惯。","enabled":true}]}
```

此示例有意演示整体替换；实际使用时应先 GET，保留不打算删除的其他维度。

## 7. 手动安排画像重建：`POST /api/v1/profiles/rebuild`

**功能与权限：** 为指定用户安排画像重建，需 `can_manage_governance=true`。处理由 Profile Worker 异步完成。

**Header：** `Authorization: Bearer <token>`、`Content-Type: application/json` 必填；`X-Request-ID` 可选。**JSON 输入：** `user_id` 必填，1～128 字符；无其他正文参数。

**响应：** HTTP `202`。`task_id` 是画像任务 ID；`status` 是该任务当前数据库状态；`available_at` 是可领取时间。此接口不返回新画像内容，后续读取 `GET /profiles` 的 `status` 与 `profiles`。

```bash
curl -X POST "$API/api/v1/profiles/rebuild" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"user_id":"user_1001"}'
```

```json
{"task_id":"tsk_profile_example","status":"pending","available_at":"2026-10-16T09:01:00+00:00"}
```

## 8. 修改个人事实：`PUT /api/v1/memories/{memory_id}`

**功能与权限：** 把一条当前有效的个人 `fact` 替换为新事实；旧事实变为 `invalidated`，新事实引用旧 ID。需 `can_manage_memories=true`。不直接编辑 `inference`。

**Header：** `Authorization: Bearer <token>`、`Content-Type: application/json` 必填；`X-Request-ID` 可选。**Path 参数：** `memory_id` 必填，目标记忆 ID。

| JSON 字段 | 必填 | 含义与取值 |
| --- | --- | --- |
| `user_id` | 是 | 目标记忆所属用户，1～128 字符且不能全为空白 |
| `content` | 是 | 新的完整事实陈述，1～8000 字符且不能全为空白；原业务/项目范围和时间边界保持不变 |
| `expected_version` | 否 | 目标当前版本，严格正整数；不一致时 409 |
| `reason` | 否 | 修改原因，最多 512 字符，写入审计 |

## 治理接口共用响应结构

第 11～19 节都要求 `can_manage_governance=true`。其中争议正文、运行里的冲突复核原因/问题、操作详情还受 `can_read_audit_content` 控制。治理运行使用数据库任务状态，可见 `pending`、`processing`、`succeeded`、`partial`、`failed`、`cancelled`；与 Add 的任务查询映射不同。

治理策略对象由下列字段组成，GET 和 PATCH 返回同样结构：

| 字段 | 含义与取值 |
| --- | --- |
| `auto_enabled` | 是否启用自动整理；默认 `false` |
| `generate_inferences` | 整理时是否生成推断；默认 `true` |
| `change_threshold` | 触发自动整理的变更数量门槛，1～10000；默认 5 |
| `idle_minutes` | 等待用户变更静默的分钟数，0～10080；默认 10 |
| `cooldown_minutes` | 连续整理之间的冷却分钟数，0～10080；默认 60 |
| `max_wait_minutes` | 等待触发的最长分钟数，1～43200；默认 360 |
| `max_memories` | 单次整理最多选择的记忆数，1～1000；默认 100 |
| `max_model_calls` | 单次整理最多模型调用数，1～100；默认 10 |
| `version` | 策略版本，发生实际变更时递增 |

治理运行对象用于第 13～15 节，字段如下。`results[]` 是按运行阶段产生的异构记录，`kind` 表示 `merge`、`inference`、`invalidate`、`conflict_review`、`skip` 等处理类型；其他字段随 `kind` 变化，不应假定所有结果都含 `memory_ids` 或 `operation_id`。

| 字段 | 含义 |
| --- | --- |
| `task_id`、`user_id`、`status` | 运行任务 ID、用户 ID、当前数据库任务状态 |
| `automatic`、`trigger_reason`、`policy_version` | 是否自动触发、触发原因、执行时策略版本；后两者可能为 `null` |
| `processed`、`selected`、`remaining` | 已处理数量、快照选中的记忆数、剩余处理量；`remaining` 可为 `null` |
| `input_memory_ids` | 本次快照选中的记忆 ID 列表 |
| `model_calls`、`token_usage` | 已记录的模型调用数和 token 用量；用量可为 `null` |
| `results`、`result_counts` | 异构处理结果数组及按 `kind` 汇总的数量；无结果时分别为 `[]`、`{}` |
| `error` | 任务错误对象或 `null` |
| `unresolved_conflicts` | 该用户当前未解决争议组数量 |
| `deferred_batches` | 因输入变化而延期的结果子集 |
| `associated_tasks` | 与本次运行相关的画像/向量/依赖/到期任务；每项有 `task_id`、`task_type`、`status`、`error`、`results`、`available_at` |
| `created_at`、`started_at`、`completed_at` | 创建、开始、完成时间；后两者可为 `null` |

## 19. 撤销治理操作：`POST /api/v1/governance/operations/{operation_id}:revert`

**功能与权限：** 在版本等条件允许时撤销一条治理操作，并记录新的反馈操作。需 `can_manage_governance=true`。不是所有操作都必然可撤销，应以当前状态和版本复核结果为准。

| --- | --- | --- |

| `Content-Type` | 是 | `application/json` |

| --- | --- | --- |

## 对接时的状态与错误定位

| 现象 | 先检查 |
| --- | --- |
| Add 返回 `pending` 很久 | Add Worker 是否运行；`GET /tasks/{task_id}` 是否终态；内部 `processing` 仍显示为 `pending` |
| Add `succeeded` 但 `results=[]` | `processing_results` 是否为 `evidence_added`、`already_exists`、无持久价值或上下文不足 |
| Search 空结果 | 记忆状态、生效/到期时间、证据、当前向量模型、来源过滤；`use_model=true` 时还要看任务适用性判断 |
| Profile 空数组 | `status` 与配置版本、Profile Worker、维度是否启用、候选是否满足长期与证据条件 |
| 治理接口能看元信息但正文为 `null` | 凭证是否有 `can_read_audit_content=true` |
| 409 | 优先检查预期版本、Add 幂等键绑定和治理撤销目标当前状态 |
