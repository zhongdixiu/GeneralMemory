# 一、建设定位：从单个 Agent 的"记住"走向统一长期记忆基础能力

随着云盘、办公、通信、邮件等业务逐步引入 Agent，记忆问题正在从"单个
Agent 能不能记住用户"演变为一个跨业务的长期基础能力问题：

> **同一用户使用多个 Agent
> 时，哪些信息应该长期保留？哪些可以共享？哪些只能在特定业务中使用？Agent
> 执行任务形成的经验如何沉淀并复用？公司统一规范又如何持续作用于不同
> Agent？**

因此，统一记忆服务的目标不是建设一个更大的"聊天记录库"，而是形成一套面向多业务、多
Agent 的长期记忆基础设施，为业务统一提供
**记忆提取、记忆管理、记忆检索** 三类核心能力。

从建设价值看，重点解决六个问题：

1.  **记什么**：识别真正具有长期价值的信息，避免所有对话无差别沉淀。
2.  **怎么更新**：随着事实变化处理补充、冲突、过期和删除，避免记忆越积越乱。
3.  **如何共享**：在授权边界内实现用户记忆、Agent
    经验和公共记忆的跨业务复用。
4.  **如何保鲜**：通过时间、状态和生命周期管理，降低过时信息对任务执行的干扰。
5.  **如何沉淀经验**：把个人或 Agent
    在任务中形成的有效方法转化为可复用资产。
6.  **如何真正作用于任务**：不是"检索到就塞给模型"，而是结合当前任务判断是否需要、适合如何使用。

**核心建设思路：统一形成、分域管理、授权共享、按需应用、全链路治理。**

# 二、记忆场景：重点建设三类记忆

统一记忆首先要回答两个问题：**这是谁的记忆，以及它可以在哪些场景下使用。**

## 2.1 用户记忆：让 Agent 越用越懂用户

用户记忆来源于用户与 Agent
的长期交互，以及用户主动维护的个性化信息。通过统一用户身份关联，使同一用户在不同业务中的长期信息可以在授权范围内持续使用。

重点包括：

-   **稳定事实与偏好**：称呼习惯、内容偏好、长期要求、内部术语等；
-   **任务连续性信息**：项目背景、当前进展、已确定事项等；
-   **长期画像与行为倾向**：在具备足够证据的前提下形成，并与明确事实区分管理。

典型体验是：用户再次说"继续上次那个方案"时，Agent
不需要用户重新交代全部背景；不同业务在获得授权后，也可以使用同一用户的稳定长期信息。

同时需要提供**记忆摘要与管理能力**，让用户知道"系统记住了什么"，并可以修改、删除或关闭相关记忆。

## 2.2 Agent 记忆：让任务经验从一次执行变成可复用资产

Agent
在执行任务过程中会形成大量可复用的工作方法，例如写作步骤、检查清单、工具使用经验、成功案例和问题修正方法。

这类记忆主要有两种来源：

-   **人工沉淀的专家经验**：由业务人员、专家或运营人员整理、审核后发布；
-   **Agent
    执行形成的经验**：从实际成功/失败案例中总结形成候选经验，再经过治理后复用。

其核心价值是：

> **把"某个人会做、某个 Agent 做成功过"转化为"后续 Agent
> 可以持续复用的能力"。**

首期不追求完全自动的经验学习，可优先支持**执行案例、人工总结经验的保存、检索和装配**，逐步向自动提炼与持续迭代演进。

## 2.3 集体公共记忆：让统一规范和组织共识持续可达

集体公共记忆由公司或团队统一维护，不属于某个单一用户或
Agent，主要承载需要在一定组织范围内持续生效的公共内容，例如：

-   公文和材料规范；
-   汇报、会议纪要等通用要求；
-   公司及部门标准名称、术语；
-   经审核后发布的公共规则和组织共识。

这类记忆的重点不是"从用户对话中学习"，而是**统一发布、统一维护、按授权装配给不同业务
Agent**。

对于会议结论、项目经验、客户背景等内容，则根据实际归属落入用户、团队、项目或业务适用范围，避免把所有组织信息都混入一个公共记忆池。

## 2.4 归属与适用范围分开管理

"谁拥有这条记忆"和"这条记忆适用于什么任务"是两个不同维度。

  -----------------------------------------------------------------------------------
  维度                    解决的问题                     示例
  ----------------------- ------------------------------ ----------------------------
  **记忆主体/归属**       这是谁的记忆或经验             用户、Agent、公司/团队公共

  **适用范围**            这条记忆在哪些任务中可以使用   邮件业务、云盘业务、项目
                                                         X、特定 Skill
  -----------------------------------------------------------------------------------

这样既可以实现跨业务共享，又可以避免"邮件场景形成的习惯被无条件带到其他业务"等记忆混用问题。

# 三、记忆如何形成：业务按场景选择采集深度

统一记忆服务不要求所有业务采集同样的数据，而是根据业务价值和隐私要求提供三档采集模式。

  --------------------------------------------------------------------------------------------------------
  模式               采集内容            主要用途                               特点
  ------------------ ------------------- -------------------------------------- --------------------------
  **完整交互模式**   用户问题 + Agent    行为偏好学习、执行经验提炼、策略优化   信息最完整，治理要求最高
                     回答 +                                                     
                     执行过程/行为信号                                          

  **用户输入模式**   用户问题与指令      用户偏好、长期要求沉淀                 最轻量

  **问答模式**       用户问题 + Agent    事实提取、对话摘要、经验沉淀           信息与成本较均衡
                     回答                                                       
  --------------------------------------------------------------------------------------------------------

建议业务从**问答模式**起步；确有执行经验学习需求的重点场景，再逐步增加工具调用、用户修改、采纳等行为信息；高敏感场景可以选择更轻量的用户输入模式。

采集到的原始交互并不直接等于长期记忆，而是经过价值判断、信息抽取、来源与状态标记后形成结构化记忆，必要时再向量化用于检索。

# 四、统一记忆服务：形成、管理、检索三大核心能力

## 4.1 记忆形成：把业务交互转化为可管理的长期记忆

业务通过 API 或插件提交交互数据后，记忆服务统一完成：

**交互数据接收 → 标准化 → 记忆价值判断 → 信息抽取/摘要 →
来源、时间、类型、状态等标记 → 分域写入 → 按需向量化。**

同时支持已有记忆资产的迁移与继承，使业务更换 Agent
框架或接入统一服务时，不需要从零重新积累。

## 4.2 记忆管理：让记忆长期可用，而不是只增不管

长期记忆会发生变化，因此管理能力重点解决：

-   用户主动补充、修改和删除；
-   重复信息整理与冲突处理；
-   TTL 到期、失效和归档；
-   来源删除后的关联处理；
-   画像、事实、向量等派生数据同步更新；
-   关键变更保留来源和审计信息。

目标是让系统能够回答：**这条记忆从哪里来、现在是否仍然有效、谁修改过、当前谁可以使用。**

## 4.3 记忆检索：先确定范围，再找相关内容

记忆应用采用两种方式：

**第一类是稳定背景常驻。**\
用户已授权、稳定且高频使用的长期画像，以及当前业务必须遵循的公共规范，可以作为基础上下文提供给
Agent。

**第二类是任务触发的按需查询。**\
Agent
根据当前任务决定是否需要查询记忆；记忆服务根据用户身份、业务/项目范围和授权边界进行过滤，再通过语义等方式召回相关内容；最终由
Agent
结合当前任务判断**必要性和适用性**，决定是否使用以及如何组装进上下文。

因此，记忆应用不是简单的"向量检索 TopK"，而是：

> **任务触发 → 范围确定 → 授权过滤 → 多路召回/排序 → 有效性过滤 → Agent
> 必要性与适用性判断 → 上下文组装。**

# 五、业务如何接入：API 与插件两种方式

统一记忆服务面向不同 Agent
框架提供两类接入方式，底层使用同一套记忆能力。

## 5.1 API 模式：业务显式集成

适合已有自研 Agent 框架、希望自行控制采集和调用逻辑的业务。

业务侧负责：

**获取交互记录 → 判断提交时机 → 调用 Add/写入接口 → 在任务需要时调用
Query/Search 接口 → 将结果交给 Agent 使用。**

记忆服务负责：

**标准化、抽取、分域存储、治理、权限过滤与检索。**

即：**业务负责把数据准备好并调用，记忆服务负责把数据变成可用记忆。**

## 5.2 插件模式：低成本自动接入

对于主流或公司统一 Agent 框架，由记忆平台提供适配插件。

业务安装插件并完成基础配置后，插件通过宿主 Agent
框架可提供的会话/消息钩子获取交互数据，按照配置自动判断提交时机，并调用与
API 模式相同的记忆接口。

同时提供 **CLI 一键接入**，用于完成插件安装和基础配置。CLI
本身不是第三种记忆协议，而是插件模式的快速安装与配置入口。

## 5.3 业务接入时只需明确五件事

1.  **记什么**：需要用户画像、事实、摘要还是 Agent 经验；
2.  **怎么采**：选择完整交互、用户输入或问答模式；
3.  **归谁所有**：用户、Agent、团队/公司公共；
4.  **谁可以用**：定义本业务、跨业务、团队及用户授权边界；
5.  **怎么查、怎么用**：定义默认检索范围以及与 Agent 上下文的组装方式。

### 架构图汇报时建议重点讲三点

**第一，业务接入统一，但不要求业务改造成同一种 Agent。**\
有开发能力的业务直接通过 API
集成；希望降低改造成本的业务通过框架插件接入，CLI 负责快速安装和配置。

**第二，统一存储不等于所有记忆混在一起。**\
底层按照记忆主体、业务/项目适用范围和授权边界组织，用户记忆可以共享但受控，Agent
经验默认不跨 Agent，公共记忆则由组织统一发布。

**第三，检索到记忆不代表一定使用。**\
记忆服务负责"在正确范围内找到可用候选"，Agent
负责结合当前任务判断"这次到底需不需要、适不适合用"，避免相关但无必要的记忆污染当前任务。

# 七、首期建设范围与推进建议

统一记忆服务不建议首期同时建设全部产品形态，而应先打通最核心闭环。

## 第一阶段：完成统一记忆基础闭环

重点建设：

-   API 接入与基础插件接入；
-   问答模式、用户输入模式的交互采集；
-   用户事实、偏好、长期要求、项目/任务事项等结构化记忆；
-   用户记忆与公共记忆的分域管理；
-   来源、时间、状态、作用域、授权等基础治理字段；
-   稳定画像常驻 + 任务触发检索；
-   记忆查询、修改、删除基础能力；
-   接入 1～2 个业务 Agent 完成端到端验证。

**阶段目标：先证明统一服务可以实现"跨会话持续、跨业务受控共享、按任务正确使用"。**

## 第二阶段：扩展 Agent 经验资产化

重点增加：

-   执行案例和人工总结经验的结构化保存；
-   Skill/任务维度的经验组织；
-   专家经验审核发布；
-   Agent 按任务检索和复用经验；
-   经验版本与效果反馈。

**阶段目标：从"记住用户"进一步走向"记住怎么把事情做好"。**

## 后续阶段：增强跨 Agent 与组织级记忆能力

在业务验证基础上进一步建设跨 Agent
授权共享、自动经验提炼、组织公共目录、记忆效果评估与持续优化等能力。

------------------------------------------------------------------------

# 八、汇报结论

统一记忆服务要解决的不是单点"记忆功能"，而是公司多 Agent
体系逐步形成后共同面临的长期上下文问题。

建设上不追求一次性做大做全，而是先形成一套统一底座：

> **业务通过 API
> 或插件低成本接入；交互数据统一形成长期记忆；不同主体和场景的记忆分域管理；在授权边界内共享；Agent
> 根据任务按需调用；全链路具备来源、生命周期和权限治理能力。**

在此基础上，第一阶段先解决**用户长期记忆与跨业务连续性**，第二阶段进一步沉淀**Agent
执行经验与组织能力资产**，逐步把记忆从"个性化辅助能力"建设为支撑多 Agent
长期工作的公共基础设施。
