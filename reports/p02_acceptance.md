## 怎么核对

逐行比较“原话及背景”“应怎样处理”“本轮实际输出”。人工复核主要判断模型理解是否符合业务需要，无须读代码或检查向量维度。措辞可以不同，意思不能变。重点看：

1. 内容有无用户原话或明确确认作为依据，有无编造细节。
2. 场景与项目条件是否完整保留，有无扩大适用范围或误丢有效记忆。
3. 重复、纠正、争议和历史的处理是否符合约定。

“应怎样处理”也需要你判断是否符合业务需求。预期本身不合理表示规则需要调整；预期合理而实际不符则是模型或实现问题。表中通过结论是 Codex 的审查，不能代替用户复核。可以直接按编号反馈有疑问的行；未核对的行保持待复核。

## 原始字段与证据

| 字段 | 含义 |
| --- | --- |
| `facts[].memory` | 候选记忆正文，必须忠实于原话并保留项目条件；有候选不等于已入库。 |
| `business_domains` | 应用场景标签；初始三类之外也可以有“方案编写”“材料管理”等。`null` 且 `scope_known=true` 表示没有业务场景限制，仍可能有项目限定。 |
| `project_limited` / `project_context` | 是否限定具体项目及其原文上下文；不是项目 ID，项目字段保持空值。 |
| `scope_known` / `skipped` | 是否理解业务适用范围及跳过原因；项目 ID 未解析不应导致有效记忆跳过。 |
| `message_ids` | 依据哪些消息；原文见案例输入。用户确认必须有用户的确认消息作为证据。 |
| `governance[].action` | 重复补证据、替代、争议或新增决策；迟到案例还带历史结束边界。 |
| `applicability` | 项目查询、模型选中候选及期望候选的对照。 |

案例输入：[虚构原话及旧记忆](../datas/p02_fact_evaluation_cases.json)。最终输出：[p02-v6](./p02_real_model_evaluation.json)。保留的历史记录：[需求修正前 p02-v4](./p02_real_model_evaluation_before_scope_correction.json)、[修正首轮 p02-v5](./p02_scope_correction_first.json)、[最初未通过记录](./p02_real_model_evaluation_first.json)。运行脚本：`scripts/evaluate_p02.py`，重跑会更新最终输出并重置为待审查。
