# Add 当前时间链路与缺省时间讨论

日期：2026-10-13。仅审查，未修改业务代码、请求协议或数据库。

## 当前字段及职责

| 字段 | 实际来源 | 当前用途 |
| --- | --- | --- |
| Message.occurred_at / SourceRecord.occurred_at | 调用方必填、带时区，数据库规范为 UTC | 消息来源时间；相对日期锚点、更新新旧判断、事实生效时间的兜底 |
| metadata.original_occurred_at | 保存调用方原始带偏移时间 | 提取时保留原来源时区，解释本周、周六等 |
| SourceRecord.created_at / MemoryTask.created_at | 数据库落库时间 | 审计和接入记录；当前没有独立的 HTTP 首次接收时间字段用于缺省 occurred_at |
| ExtractedFact.effective_at / MemoryItem.effective_at | 优先模型输出，否则取该事实引用的目标 user 消息最大 occurred_at | 事实状态起点；默认 TTL 起点；更新倒退检查；Search/Profile 的尚未生效过滤 |
| ExtractedFact.expired_at | 模型输出的明确截止或历史区间结束 | 覆盖默认 TTL；当前也容纳历史状态边界 |
| MemoryItem.expired_at | 模型截止优先，否则 effective_at + 分类默认天数 | 当前使用截止；到期过滤和状态转换 |
| metadata.explicit_expired_at | 模型输出的 expired_at，未加默认 TTL 时的原始值 | 判重时区分用户期限和系统 TTL |
| metadata.source_occurred_at | 被该事实引用的目标 user 消息最大来源时间 | 与新消息来源时间比较，防止迟到覆盖 |
| 事件发生时间 | 没有独立字段，可能出现在正文，也可能被模型填入 effective_at/expired_at | 当前区分依靠模型理解，没有明确事件日期字段或完整提示契约 |

occurred_at 指消息发生/声明时间，不是“动物园出行”等正文中事件的发生时间。接口必填要求针对调用方，通常应由接入程序读取原消息发送时间，不应让聊天用户填写。

## 当前处理顺序

1. 接口验证 occurred_at 存在且带时区，省略/无时区会返回校验错误；不自动填系统时间。
2. 保存来源 UTC 时间、原时区偏移、timestamp_origin（默认 source）。
3. 模型接收原偏移时间。adapter_observed 在模型输入中被置为 null，禁止解释相对日期。
4. 模型输出 effective_at、expired_at、temporal_kind、retention_kind。
5. historical 若缺完整起止区间被跳过；adapter_observed 参与明确变更会被 UNKNOWN_EVENT_TIME 跳过。
6. 最终 effective_at = 模型 effective_at 或引用目标 user 消息最大 occurred_at。
7. 最终 expired_at = 模型 expired_at，否则 temporary +30 天、regular +180 天、long_term 无默认到期；这些默认天数从最终 effective_at 起算。
8. 治理对来源声明时间和状态生效时间分别检查；提取阶段尚未明确事件时间与状态时间的区别。
9. 非争议新记忆截止 <= 当前系统时间时写 expired，否则写 active。Add 结果检查 active 和到期时间，但未检查 effective_at <= now；Search/Profile 会检查。

之前将默认 TTL 简化为“从来源时间起算”不够准确。仅在模型没有输出 effective_at 时才成立。

## 确认的实现缺陷

### 1. Add 和 Search 的时间可用性判断不一致

动物园实际快照：来源 2026-10-13 10:00 +08:00；记忆 09:43:50 +08:00 落库；effective_at=10:00。Add 返回该记忆，Search 在 10:00 前会因尚未生效排除。

这是历史快照与当前过滤条件的交叉验证，未执行历史时点的数据库 Search。接口文档称 results 是提交时可用记忆，当前判定缺少生效时间条件。

输入本身包含未来消息时间，是另一项契约问题：当前只校验格式/时区，不限制未来 occurred_at。应区分允许的时钟误差与把事件日期错误填成消息时间；未来规则生效日期应走 effective_at，而非 occurred_at。

### 2. 最终有效区间缺少校验

模型 schema 仅在两个时间都存在时检查 expired_at > effective_at。effective_at=null 后由来源补齐时，可能产生截止早于生效的区间。当前代码及数据库模型没有最终区间约束兜底。

### 3. 确定性时间拒绝被当作可重试模型失败

迟到替代和状态时间倒退抛 ProviderError，进入模型失败重试；固定时间条件不会因重试改变。应区分语义拒绝与暂时模型失败。

## 语义和策略问题

- effective_at 同时用于事实状态起点、默认记忆保留期起点。若今天声明“自2020年至今，客户联系人一直是李明”，模型填 2020 年生效，则 regular 默认截止也落在 2020 年，今天首次提取就已过期。本地合成候选确认这一公式。默认保留期是否应从声明锚点起算需要重新约定；这与现有文档一致，但业务效果存在缺陷。
- effective_at 缺少事件日期与计划存在时间的明确区分。如果填成未来出行日，会导致提前检索不到、取消 update 被拒绝。本地已复现候选进入治理时的倒退拒绝，未声称每次模型必然这么填。
- expired_at 同时承担业务适用截止、历史状态区间结束和系统保留期。过去居住区间结束不等于“曾居住过”事实失去记忆价值；按用户澄清，“以前在北京住过”应 regular 保存，不要求完整区间。
- adapter_observed 对模型隐去来源时间，但服务在 effective_at 缺省时仍用这个观察时间作为状态起点和 TTL 起点；变更又被禁止。它允许的用途需要明确，不能只说“时间未知”。观察时间可作为存储保留期锚点，不应自动证明历史状态或相对日期。
- 历史区间不完整就全量跳过是过度限制；已有日期应保留，没有日期不杜撰。仅在时间缺失阻碍事实含义或变更裁决时返回不足。

## 建议的时间职责

1. 消息时间：用户何时说这句话，用于相对日期和声明先后；优先真实发送时间，可信实时缺省采用首次接收时间。
2. 事实生效时间：规则/状态何时开始适用。没有明确起点通常采用声明时间；用户说“下月开始”才设置未来起点。
3. 事件时间：出行/会议/过去经历发生的日期，优先补全在正文中，保留用户精度。计划现在已经存在，不应等到出行日才生效。
4. 记忆到期时间：按分类默认计算或采用明确期限。用户输入的事件日期、经历区间不应无条件变成记忆截止。
5. 接收时间：服务什么时候收到数据，供审计和可信实时时间兜底；历史导入不得用它重解释过去的“本周”。

默认 TTL 的建议：通常从声明锚点起算，重复证据是否续期沿用当前“不续期”规则；明确未来才生效的规则可以从未来生效时间起算。过去事件日期不应拖早 TTL。此为建议，尚未修改公式。

计划事件过后是否按事件边界退出当前检索，是额外的计划类型策略，应明确约定；不能把事件日期直接称作用户明示的记忆保存期限，也不能推断计划已经执行。

## occurred_at 省略是否合理

当前必填是保护来源时间真实性的接口设计，不是实现 Bug；但对实时接入不方便，且会诱发调用方随意填时间。

建议默认 Add 是实时消息接入：发生时间省略时在首次接收补齐，明确其 server_received 来源及用户时区。原消息发送时间可取得时仍优先提供它。

历史导入必须显式识别，或使用独立入口；其来源时间缺失时保存未知语义，可以保留普通事实，不能用接收时间解析相对日期或证明其新于已有状态。history_messages 也不能因为省略日期就默认解释成今天。

自动补齐应在请求重放/来源复用策略中处理，不能简单在每次 schema 解析生成 now，因为当前指纹和来源一致性检查都包含时间；相同请求重试必须复用第一次的补齐值。

以上建议的主要前提是默认 Add 的实时契约。是否支持历史来源与实时来源混在同一请求，以及缺省时区，由接口契约明确后再实施。
