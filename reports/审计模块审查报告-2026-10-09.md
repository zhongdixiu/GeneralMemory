# 审计模块审查报告

审查日期：2026-10-09。范围：当前工作区代码、数据库迁移、设计文档、相关测试，以及 `.env` 指向数据库的只读查询。工作区已有未提交修改，本报告以当前文件内容为准。

## 1. 结论

`memory_audit_log` 的基本结构可以保留，但当前审计语义和阅读方式需要改造。

问题不只是字段多，而是业务变更、治理决策、任务通知和技术维护混在一起；同一字段在不同写入点承担不同含义；部分真实业务变更无法通过目标 ID 完整追溯。

建议先修正记录的含义、目标和链路，再提供面向人的查询展示。当前没有证据支持立即拆成多张审计表、引入独立日志系统或做分区。

## 2. 实际数据核对

当前连接库的 Alembic 版本为 `0005_atomic_profiles`，审计记录共 **43 条**，涉及一个租户，记录时间覆盖 2026-09-28 至 2026-10-09。该样本不能代表生产规模。

| 记录内容 | 条数 | 阅读上的问题 |
| --- | ---: | --- |
| 画像生成、失效、迁移 | 16 | 同时包含旧属性键和新独立陈述的历史形态 |
| 事实创建、证据补充、冲突、TTL 分类迁移 | 14 | 事实创建和证据补充拆开，冲突动作命名不准确 |
| 抽取任务入队、治理推断操作 | 6 | 入队通知与实际治理结果混在任务类型中 |
| 来源接入 | 5 | 只看来源日志无法看到抽取结果 |
| 向量新增、删除 | 2 | 技术维护记录与业务变更并列 |

其他核对结果：

- 40/43 条没有顶层可读原因 `reason`；某些实际原因放在 `state_after.reason`。
- 9/43 条没有 `correlation_id`，分别是 3 条画像迁移和随后 6 条画像创建。
- 33/43 条没有有效的 `state_before`。INSERT 无前态、诊断事件无前态都是正常情况，不能把这个比例直接当成缺陷率。
- 5 条事实记忆都有以自身为目标的创建记录；唯一的推断记忆没有以自身为目标的创建审计，相关生成记录挂在治理任务上。
- 已检查的 `memory`、`task`、`profile` 目标没有指向不存在对象的记录。此检查不等于完整引用校验，也不要求删除审计的目标对象继续存在。
- JSON 空值混用：`state_before` 有 32 个 SQL NULL、1 个 JSON `null`；`state_after` 有 1 个 JSON `null`。直接对 JSON 执行 `jsonb_object_keys` 会在 JSON `null` 上报错；仅用 `IS NULL` 也会漏统计 JSON `null`。
- 表只有主键及三个枚举 CHECK，没有用户自定义触发器；当前连接角色有 UPDATE、DELETE 权限。“只追加”尚未由当前数据库配置强制保证。

自增 ID 不等于行数。当前最大审计 ID 为 12561，但实际只有 43 条；序列间隙不能单独证明数据丢失。

## 3. 字段结构是否合理

当前共 13 个字段，定义见 `src/memory_cmic/models.py:699`。

| 字段组 | 字段 | 判断与建议 |
| --- | --- | --- |
| 身份与隔离 | `id`、`tenant_id`、`created_at` | 必要；普通列表只需展示时间，流水 ID 可收起 |
| 事件与目标 | `action`、`target_type`、`target_id`、`reason_code` | 必要；需要统一定义，普通列表展示中文事件和目标摘要 |
| 操作者 | `operator_type`、`operator_id` | 必要；明确指发起者还是执行者，目前两种含义混用 |
| 原因 | `reason` | 有价值；已有真实决策原因应放在这里，固定事件中文名称可由读取层映射 |
| 链路 | `correlation_id` | 必要；表示一次处理链路，不应兼任任务 ID |
| 变更 | `state_before`、`state_after` | 保留；明确为“本事件涉及字段的前后值”，不能承诺完整对象快照 |

不建议为了减少字段而把目标、操作者和链路全部塞进 JSON。这样只会让查询和理解更困难。

文档也有小幅漂移：冻结版字段表仍将 `operator_id` 写为 VARCHAR(64)，当前模型和数据库迁移已扩为 VARCHAR(128)。后续应同步字段说明。

也不必直接增加 `event_type`：现有 `reason_code` 实际已经在表达事件类型，例如 `FACT_EXTRACTED`、`PROFILE_REBUILT`、`VECTOR_DELETE`。先定义事件字典和写入契约，避免再增加一套含义重叠的分类。

## 4. 具体问题与证据

### 4.1 日志顺序与业务含义冲突

`src/memory_cmic/worker.py:818` 写入 `FACT_EXTRACTED` 前，先调用 `_add_evidence`；后者在 `worker.py:367` 写入 `FACT_EVIDENCE_ADDED`，动作是 UPDATE。

实际数据中，同一记忆的日志 ID 4676 为“补充证据 UPDATE”，4677 才是“创建记忆 INSERT”，且时间戳相同。其他四条新事实也存在相同顺序。

这不是数据库先更新了不存在的记忆，而是审计事件的记录顺序使业务时间线产生误导。新建时的证据是创建的一部分；重复陈述给已有记忆增加证据才是独立的补充事件。

建议：新建记录包含初始证据关联，或者明确先记录创建再记录证据创建；已有记忆的证据补充继续单独记录。不要仅调整显示排序来掩盖写入语义。

### 4.2 真实目标记录错误或缺失

- `src/memory_cmic/consolidation.py:347` 的 `_record` 收到 `memory_id`，却把审计目标固定为 `task`、任务 ID，并复制整个 `details` 到 `state_after`。其中推断生成没有另写 memory INSERT；`_infer` 的详情甚至不包含新推断 ID，必须再关联 `governance_operation.memory_id` 才能定位。
- 实际审计 ID 8542 是 `GOVERNANCE_INFERENCE / task / UPDATE`；库中对应推断记忆没有自己的创建审计。按 `(tenant_id, target_type='memory', target_id)` 查询无法回答它如何产生。
- `src/memory_cmic/api.py:169` 将 `GOVERNANCE_POLICY_CHANGED` 的目标记成 `task`，`target_id` 却是租户 ID。该问题由代码确认，当前 43 条样本里没有该事件。
- `src/memory_cmic/lifecycle.py:426` 将进入 `disputed` 状态也记为 INVALIDATE。实际 ID 4684 的前后状态是 `active → disputed`，不是 `active → invalidated`。

建议：实际变更以 memory/profile/source 为目标；治理策略使用真实的 `governance_policy` 目标类型；进入争议状态用 UPDATE 加 `FACT_DISPUTED` 事件。任务执行身份另行关联。

合并涉及多个对象时，应保证被失效记忆和保留记忆的关键变化都能从各自历史追溯，不能只保留一条任务操作描述。

### 4.3 状态 JSON 没有一致契约

实际 `state_after` 至少存在以下不同结构：

| 事件 | 当前主要内容 |
| --- | --- |
| `FACT_EXTRACTED` | `content`、`status`、`governance_action` |
| `FACT_EVIDENCE_ADDED` | `evidence_group_id`、`task_id`、`message_ids` |
| `PROFILE_REBUILT / INSERT` | `key`、`value`、`basis_ids`、`version` |
| `GOVERNANCE_INFERENCE` | `operation_id`、`content`、`basis`、`source_ids`、`source_refs`、`reason`、`version` |
| `VECTOR_UPSERT` | `model_id`、`content_hash` |

有的是对象状态，有的是证据关系，有的是执行上下文。画像失效前态只写 version，后态却写 version 和 status；创建事实缺 version，创建画像缺 status。这些记录可解释，但不能直接用于统一差异展示，更不能据此完整重建对象历史。

建议：前后状态只存本次审计所涉及的业务字段；字段变化尽量对称。采用明确的事件结构，区分必要的状态值与关联信息。新写入代码统一由一个小型审计写入函数处理 SQL NULL 和基础字段，避免各模块继续自行拼接。只有当前事件确需额外上下文时才增加一个 `context` JSON，避免一次性迁入所有现有字段。

已有 JSON `null` 在读取时兼容；如以后需规范旧数据，应走可追溯的维护方案，不能静默改写历史。

### 4.4 链路归组与任务定位混淆

- `src/memory_cmic/ingest.py:246` 将请求 ID 截断到 64 字符当作 `correlation_id`。请求 ID 是客户端可提供值；两个相同前缀的长 ID 或重复 ID 可能把不同处理链路混为一组。当前样本未观测到多个 fact_extract 任务共用链路的情况，不能将这个可能性描述成已发生事故。
- `src/memory_cmic/consolidation.py:1181` 的撤销审计使用 `operation.task_id` 作为 correlation，而原操作使用 `task.correlation_id`。两者不是同一个标识，直接按原链路归组会漏掉撤销。
- `migrations/versions/0005_atomic_profiles.py:35` 入队重建任务时没有链路 ID；迁移审计也没有链路 ID，实际对应 9 条无法直接归组的记录。
- `task_id` 只出现在部分 `state_after` 中，其他事件必须依赖 correlation 反查任务。
- `src/memory_cmic/profile.py:180` 会复用已有 pending 重建任务，直接返回该任务，新的触发链路不再记录。同一个画像任务可能承接多次请求，不能假设一个 correlation 天然覆盖所有触发者；当前样本没有据此确认具体遗漏事件。

建议：生成独立处理链路 ID，并传递给各阶段；后台和迁移批次也建立链路。任务执行产生的日志使用显式、可空的 `task_id`。归并任务保留多个触发关联，不能仅覆盖或继承第一次请求 ID。撤销是新的操作，可建立新链路并通过 `operation_id` 或原链路关联回原操作，不应把原任务 ID 填入 correlation 代替这层关系。

### 4.5 业务审计与运行诊断重复

`src/memory_cmic/worker.py:1148` 将未通过范围、时间等校验的候选记成 source UPDATE，但来源对象并没有因此发生业务字段变更。相同诊断已经保存在 `memory_task.payload.execution.diagnostics`。

`src/memory_cmic/consolidation.py:361` 则将 `governance_operation.details` 整份复制到审计 JSON；其中可能包含来源内容、推断依据、证据范围快照，既增加阅读噪声，也造成详情重复。

建议：任务诊断留在现有任务诊断位置；审计记录实际业务变化。治理审计保留目标、前后变更、原因与 `operation_id`，撤销所需的复杂快照仍由 `governance_operation.details` 承载。必要的历史内容快照应保留，不能为了省空间把审计变成全部依赖当前对象状态的引用。

向量维护记录可保留为技术明细，但默认业务列表收起。`embedding` 的身份是租户、memory_id、model_id 的组合；当前 target_id 只有 memory_id，阅读层必须一并使用 model_id，不能把它当作独立 embedding ID。

### 4.6 缺少面向人的审计读取层

`src/memory_cmic/api.py` 目前提供治理运行和操作查询，没有专门的审计列表、对象时间线或链路查询。`run_id/operations` 也只覆盖治理操作，无法代替来源接入、事实抽取和生命周期审计。

建议读取层默认回答四件事：何时、哪个对象、发生什么、为什么。ID、证据、任务、向量、原始 JSON 在详情中展开；提供对象历史和处理链路两个入口。

展示示例（非实际用户内容）：

```text
14:41  创建事实记忆  “用户希望邮件简洁”
       原因：从本轮用户消息中抽取；初始证据 1 条

14:47  标记记忆存在争议
       状态：active → disputed
       原因：新陈述与原记忆冲突，保留双方等待确认

       展开技术明细：向量删除、画像重建、任务与链路 ID
```

固定事件中文名称从事件字典生成；模型或管理员的具体理由使用 reason，缺失时显示“未记录具体原因”，不虚构旧日志的理由。

读取必须按 tenant 限制范围，并处理内容授权。设计文档明确“管理员身份不自动获得查看用户原始内容的权限”；当前治理操作接口直接返回包含内容的 details，权限只检查治理管理权限。新增审计查询时应明确落实该内容权限要求，不能直接把所有快照开放给治理管理员。

### 4.7 “只追加”与测试覆盖尚不完整

设计文档要求只追加、不更新、不物理删除；当前代码没有审计更新接口，但实际连接角色能够 UPDATE/DELETE，数据库也没有阻止改写的触发器。开发库的结果不能直接推断生产权限配置，但说明当前环境仅依靠调用方自觉。

现有测试验证了部分日志是否存在、数量、reason_code 和 correlation，部分生命周期/链路测试由测试代码自己插入日志。它们不能证明所有实际写入路径均满足统一审计契约。

建议业务运行角色只授予所需 SELECT/INSERT，迁移及测试清理使用独立权限；不要给所有测试环境直接加禁止删除触发器。针对下面的语义缺陷补充少量回归测试即可。

## 5. 最小改造顺序与验收

| 优先级 | 工作 | 验收标准 |
| --- | --- | --- |
| P1 | 修正事实创建顺序、推断目标、策略目标、争议动作和错误失效原因 | 新建时间线不会先 UPDATE 后 INSERT；每个新推断有自身 INSERT；策略日志目标准确；争议不会被描述成失效 |
| P1 | 统一事件字典、真实原因和关联传递 | 同一事件语义一致；具体理由有明确位置；后台迁移能归组；撤销能关联原操作 |
| P1 | 增加最小读取/展示能力 | 支持对象历史与链路查询；列表无需阅读原始 JSON；目标和内容的授权范围正确 |
| P2 | 统一部分状态结构和 JSON 空值；按需要增加显式 task_id | 相同事件可一致解释；前后变化可展示；任务可直接定位；SQL NULL/JSON null 均能兼容读取 |
| P2 | 去掉新增日志中的诊断重复和治理详情整份复制 | 业务审计保留必要变更与证据关联，详细诊断及撤销快照留在已有事实来源 |
| P2 | 落实业务角色只追加权限 | 业务角色可以写入审计，无法改写或删除；维护和测试流程仍有明确权限 |
| 后续按需 | 用户筛选字段、列表索引、归档或分区 | 由实际查询需求、执行计划及数据增长触发，不凭当前 43 条样本预先建设 |

错误失效原因的具体路径：`consolidation.py:688` 的治理主动否定和 `consolidation.py:1045` 的人工撤销推断均调用 `invalidate_memory`，而后者统一写 `EVIDENCE_INCOMPLETE`。这会把主动治理或人工否定误记为证据不足，需要让该路径携带实际原因。

新读取层应兼容旧 target/JSON 结构和事件码；旧事实中缺失的具体理由、任务身份不能凭空补齐。历史日志不做静默重写或批量删除。
